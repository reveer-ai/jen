# Decisions

Newest first. Each entry gives the decision and why. When an entry is superseded, mark it and link the entry that replaces it.

## 2026-11-19

Set by the maintainer in their review of [JEN-25](https://linear.app/reveer/issue/JEN-25):

- **`jen` assumes no provider: the base URL is required, like the model and the key.** *Why:* set by the maintainer; jen is model-agnostic, and an empty answer meaning OpenAI's endpoint made one provider the default. Settings saved without one ask only for it at the next start, keeping the rest and the owner token.
- **Every line of `jen`'s own starts lowercase, and in a terminal a blank line comes before and after a command's output, and after the answers to its questions.** *Why:* set by the maintainer, matching the `jen: ` errors. The first blank line is written with the first output, not as `jen` starts, so a slow reply doesn't arrive in two steps. Text from an agent or the user is written as it is. The blank lines go only to stderr, and only when it's a terminal, so redirected output is unchanged.
- **An unquoted `?` or `*` in zsh is left to the user's shell: `jen help` says to add `alias jen='noglob jen'` to `~/.zshrc`.** *Why:* zsh fails the command before `jen` runs, so `jen` can't fix it. *Rejected:* editing the user's `~/.zshrc` at install, which `npm link` can't do and which would change a file outside Docker.

Made in [JEN-25](https://linear.app/reveer/issue/JEN-25), fixing its implementation review:

- **A root's notice that it gave up on its model is marked `"gaveUp": true` on its `error` event, and ends a query in `jen` with exit 1.** *Why:* a root that gives up saves nothing, so `jen` otherwise waited forever, as the maintainer's hand check hit with a mistyped base URL. A field on the existing event leaves the UI page, which shows every `error` event's message, unchanged. A message clears the notice, and an agent with a message waiting when its last retry fails tries again rather than giving up, so a notice that reaches a query is about that query. *Rejected:* an event type of its own, which the page would need to learn; and matching the notice's text, which is the agent's own wording.

## 2026-11-18

Made in [JEN-25](https://linear.app/reveer/issue/JEN-25), aligning on its proposal with the maintainer. The proposal is in `openspec/changes/add-jen-command/`:

- **The Distribution milestone is two tasks: the `jen` command and its interactions ([JEN-25](https://linear.app/reveer/issue/JEN-25)), and publishing it as `jenai` ([JEN-26](https://linear.app/reveer/issue/JEN-26)).** *Why:* set by the maintainer. The command is a task of its own, and publishing can run beside it.
- **The user addresses every root by name, with `@<name>`, and creates roots with `jen new <name>`.** The commands are `jen new <name>`, `jen @<name> <query>`, `jen @<name> open`, `jen list`, `jen stop @<name>` and `jen stop all`. *Why:* set by the maintainer. A user has several roots, each keeping its sub-agents over time. A current or default root can come later.
- **The runtime starts when a command needs it and runs until `jen stop all`.** *Why:* a root's UI is served through the runtime, a root's work can outlast its reply, and a stopped root wakes for a message. *Rejected:* stopping the runtime when a query finishes, the maintainer's first thought, which would kill the UI the query just built.
- **A new image stops every agent, and nothing migrates stored state between versions.** *Why:* set by the maintainer. A rebuilt image otherwise reaches an agent only after a stop and start by hand. Migration waits until jen has users whose agents must survive an upgrade.
- **All of jen lives in Docker, settings included, and `jen uninstall` deletes all of it, npm package too.** `jen` asks for its settings and keeps them, with the owner token, in a Docker volume of its own, which the runtime never reads. While the runtime runs, `jen` reads the token from the runtime's container. *Why:* set by the maintainer: everything of jen's in one place, and nothing left behind when jen is deleted. npm runs no script of a package at uninstall (npm v7 and later), so only a command of jen's can clean up Docker. *Rejected:* a file in `~/.config/jen/`, the one piece of jen outside Docker. The installed package's folder, which every upgrade replaces. The system keychain, which Node has no API for and is a second place again. A volume the runtime owns, which would make the runtime stateful.
- **`jen @<name> <query>` shows a line for each step of progress, then the reply.** *Why:* set by the maintainer.

Made in [JEN-25](https://linear.app/reveer/issue/JEN-25)'s design (`openspec/changes/add-jen-command/design.md`):

- **`jen` reaches the engine through the user's `docker` command, not the Engine API over a socket.** *Why:* only the command resolves the user's Docker context and `DOCKER_HOST`; the socket's path differs between Docker Desktop, Colima, OrbStack and remote engines. *Rejected:* running `src/runtime/docker.ts` on the host, which would reimplement contexts.
- **Settings are asked for in the terminal, not edited in `$VISUAL` or `$EDITOR`.** *Why:* an editor puts the key in a file on the host, and may copy it into swap, backup or undo files that `jen uninstall` can't find. Discussed with the maintainer. An editor becomes worth it once there are enough settings that aren't secret.
- **A new image is detected by image ID, not by version.** *Why:* a checkout has no version, and a rebuilt image is exactly the change that should reach agents.
- **Every root has a name, given by the owner at spawn and fixed for the root's life.** The runtime refuses a missing, malformed or taken name, and a sub-agent has none. *Why:* a root without a name can't be reached from `jen`, so requiring one keeps the tree and the command in step. *Rejected:* optional names.
- **The agent's event stream sends `synced` once it has sent every item saved so far, and a query's reply is read only after one.** *Why:* `jen` must tell history from what's new, and know a model response has fully arrived before deciding it had no tool call. *Rejected:* waiting for a quiet moment, as the live checks' `replies()` does, which a slow relay can split a response across; and skipping history by matching the query's text, which may already be in the conversation.
- **JEN-25's live verification is accepted with the behavior check failing on the known Luna timeout flake.** Every other live check passed with named roots. The behavior check failed in both passes on 2026-11-18, each time only the files task's run `files-1`, where `openai/gpt-6-luna` gave `run_command` a `timeout` of 120000, outside 1 to 600 seconds, and the runtime refused the call. *Why:* set by the maintainer. The same fault failed the check on `main` on 2026-11-13 ([environment.md](environment.md) lists it with the other known flakes), and JEN-25 changes no agent tool, instruction or model call. A clean pass would only have shown the flake didn't come up.

## 2026-11-16

Made in [JEN-21](https://linear.app/reveer/issue/JEN-21). The proposal and design are in `openspec/changes/archive/2026-11-16-keep-key-in-runtime-and-agents-offline/`:

- **The runtime proxies agents' model calls at `POST /model/responses`, accepts only the request shape jen's Responses adapter builds, and sets the model itself.** No agent holds the key or the endpoint. *Why:* set by the maintainer with the proposal. Forwarding the provider's whole API hands every agent all the key can do, and forwarding the Responses call as it comes leaves the provider able to fetch any URL a request names, such as an image, a file or a remote MCP server. An allowlist fails closed on fields a provider adds later. Setting the model keeps an agent off pricier models and variants such as OpenRouter's `<model>:online`. *Rejected:* refusing only what's known to reach out, which fails open.
- **Agents' network is internal, with IPv6 off and an isolated IPv4 gateway (Docker Engine 28.0 or later).** *Why:* measured on 2026-11-16 on Docker Desktop: a plain internal network leaves the bridge's gateway address on the engine's host, where a container reached a listener on the host network. The isolated gateway leaves no such address. The boundary check probes every address the host has.
- **No code migrates the old `jen` network.** Docker can't make an existing network internal, so a runtime that finds one by its name uses it as it is. *Why:* set by the maintainer: jen has run only on their laptop, which was migrated by hand.
- **WebRTC out of a UI's sandboxed frame stays open, as a known gap.** *Why:* measured on 2026-11-16 in Playwright's Chromium 158 and WebKit 27.2: an `RTCPeerConnection` in the frame, or in a `srcdoc` frame nested in it, sends STUN to any host it names, and CSP's `webrtc 'block'` changes nothing. Closing it from the bridge would mean intercepting every way a document makes a frame, which has no end. What can leave is only what the agent put in its UI and what the viewer types, from the viewer's browser, and a breach shows only in the viewer's own traffic. Firefox and Safari weren't measured.

Made in [JEN-4](https://linear.app/reveer/issue/JEN-4), with the maintainer:

- **An agent is jen's unit, and each agent has an owner, a person or an organization.** People have their own agents, which message each other, and a person's agents stay theirs. What belongs to many people, such as a company's messaging, lives in an agent they share, which runs where all of them can reach it. *Why:* set by the maintainer. Shared data needs one home: copies kept in each person's agent would have to stay in sync while their owners are offline. And if people talked only through their own agents, every message would take a model call, which 2026-11-14 rules out. Nothing in this project builds sharing or messaging between agents that aren't parent and child.
- **jen ships as one npm package, `jenai`, whose command is `jen`, and no separate website serves it.** A hosted jen is the same package on a machine others can reach. *Why:* set by the maintainer. The runtime already serves every agent's page, so generating UI needs no server of jen's own. A server adds only being always on and reachable from other devices and people.
- **The Distribution and hosting milestone becomes Distribution: the package only.** Where shared agents run, with login and TLS, waits for a later project. *Why:* set by the maintainer, to do only what's known to be needed now. jen can be built out on the package for a while before agents need to live in the cloud.

Made in [JEN-23](https://linear.app/reveer/issue/JEN-23):

- **An approved `tend` proposal lands in the pass's pull request unless it needs a design, which gets an issue of its own.** *Why:* set by the maintainer, in [JEN-23](https://linear.app/reveer/issue/JEN-23). A proposal that needs a design needs a proposal to align on, sometimes live runs, and an estimate against the cycle's capacity, and the pass's fixes shouldn't wait on it. Refines in part 2026-11-09's rule that a pass's findings get no issues of their own.

## 2026-11-15

- **The page's activation check stays, and the bridge keeps focus in a text field during a press so Safari counts the click.** Safari loses a click's activation when the press takes focus out of a text `<input>` the user typed in, so the page dropped the most common form's ask. The cause, unmeasured on 2026-11-14, is measured in [JEN-22](https://linear.app/reveer/issue/JEN-22) and its change, `keep-input-focus-for-asks`. *Why:* set by the maintainer. Without the check, a UI could message the agent as the owner with no one acting, for example in a loop on load, and nothing caps an agent's spend yet. *Rejected:* a confirm bar the page shows for an ask without activation, since most forms in Safari would have taken two presses.

## 2026-11-14

Made in [JEN-18](https://linear.app/reveer/issue/JEN-18)'s implementation review, checking it against the direction below. The design is in `openspec/changes/archive/2026-11-14-add-agent-ui/`:

- **JEN-18 builds only the web shell's foundation, and tells the agent nothing about how to answer.** It keeps:
  - the fixed page and the sandboxed frame
  - the bridge, with one request
  - publishing with versions, and the live swap
  - the textbox as version 0
  - the routes

  `publish_ui`'s description says what the file must be, what the bridge does and what the page shows. Nothing says to answer by publishing or that every UI must let the user keep talking to the agent. *Why:* set by the maintainer. The first implementation taught every agent to answer each action by republishing, the habit the direction below rules out. How an app shows what the agent says belongs to the data layer. Supersedes in part 2026-11-13's "the agent answers the textbox by publishing … its instructions say all this".
- **Offering `publish_ui` to every root with `workspace` is kept, though it makes `openai/gpt-6-luna` get files wrong more often.** With the tool offered, the behavior check's files task went wrong in 12 of 54 runs, against 0 of 24 without it, though Luna never called the tool. The tool's wording made no clear difference. *Why:* set by the maintainer. *Rejected:* offering the tool only once the agent's page is opened, which changes the tools partway through a conversation and stops an agent building an app before anyone asks.
- **The bridge's request to the agent is `jen.ask`, not `jen.act`, and an ask carries only its version and context.** *Why:* asking the agent is one of the bridge's fixed requests. `act` came from 2026-11-10's "interfaces are dumb", where every interaction was an action for the agent.
- **Safari dropping a click's ask doesn't block JEN-18; [JEN-22](https://linear.app/reveer/issue/JEN-22) fixes it.** *Why:* set by the maintainer. A probe found Safari often counts a click as no activation even inside the frame, while Enter always counts, so the cause is Safari's and still unmeasured (design, Risks). JEN-18 works in Chromium, which its checks cover.

Made with the maintainer, checking [JEN-18](https://linear.app/reveer/issue/JEN-18)'s direction against what jen is for. None of it is scoped yet; the work it calls for is under UI in [ideas.md](ideas.md):

- **jen generates the software an organization runs on, and agents build what should be built without being asked.** Messaging, boards and the rest are built for the organization, in place of separate products that don't talk to each other. Many people use what an agent builds and talk to each other through it. jen isn't a tool people tell what to build. *Why:* set by the maintainer.
- **An agent's app runs without the agent, and the agent sees everything that happens in it.** A message between two people goes through code the agent wrote, with no model call. Every write to the app's data reaches the agent, which decides what starts a turn. The agent also writes into a running app, such as an idea filled in while people discuss it, and changes the app itself only when its structure should change. *Why:* set by the maintainer. A model turn on every interaction is too slow and costly for software people use all day, and regenerating an interface throws away the familiarity people build. Supersedes in part 2026-11-10's "interfaces are dumb" and 2026-11-13's "a UI shows only what the agent publishes".
- **jen ships capabilities, not components.** jen's fixed part is the shell (identity, access, the sandbox host, moving between apps, notifications), the bridge's small, fixed set of requests (read and watch data, write data, who's here, ask the agent, files, open another app), and the data sync behind them. A capability belongs in jen when it's the same for every organization and hard to get right by generating it. What an organization does is generated. *Why:* set by the maintainer. jen generates; a component list it maintained would grow forever.
- **Stock jen looks minimal, plain and beautiful. An organization's agent takes over the look, and its sub-agents follow.** Familiarity comes from design and code passed down the tree, not from jen. Agents also use the open-source ecosystem, such as React and component kits. *Why:* set by the maintainer.
- **The web is the first surface, refined over time, and no design rules out others.** Generated code that reaches out only through a host that knows the viewer and checks each request fits any surface; the iframe, `postMessage` and user activation are how the web shell does it. Data belongs to the agent, not to a UI, so a UI on any surface, and any outside application, is one client of the same data. *Why:* set by the maintainer. jen could be a TV menu.

## 2026-11-13

Made in [JEN-18](https://linear.app/reveer/issue/JEN-18), reviewing its design. The proposal and design are in `openspec/changes/archive/2026-11-14-add-agent-ui/`:

- **An agent publishes its UI as one file, `ui/index.html`, sent as it is, which must stand alone.** Scripts and styles are inline, images and fonts are `data:` URLs, and nothing is fetched. The agent can keep and do whatever it likes in its workspace before it publishes. `publish_ui` refuses only a missing file, one that isn't UTF-8, or one over 4 MiB. *Why:* set by the maintainer, to keep the task simple. Models write self-contained pages well, and jen keeps no bundler. *Rejected:* jen bundling `ui/` with `parse5` and a hand-kept list of the HTML and CSS that loads files. A check that refuses a published file's URLs can come later if the UI check on Sol shows models breaking the rule.
- **Every agent starts with a shipped textbox that shows nothing of the conversation, and from there its UI is all the agent's.** The agent answers the textbox by publishing a UI, decides what each UI shows, and must give the user a way to keep talking to it. Its instructions say all this (*superseded in part 2026-11-14:* nothing tells the agent how to answer). *Why:* set by the maintainer. The conversation isn't always what the user needs to see. *Rejected:* a starting UI that shows the thread, and the agent writing its own first UI, which needs a turn no message started and leaves no way in if that UI is broken.
- **A UI shows only what the agent publishes, and can't read the conversation.** The agent answers the page by publishing; its text replies aren't shown there. The bridge gives a UI only `jen.act` and `jen.version` (*renamed 2026-11-14:* `jen.ask`). *Why:* set by the maintainer, to build a foundation to extend while using it. The agent communicates through its UI, and a transcript belongs in a pane jen could draw outside the frame. *Rejected for now:* `jen.subscribe`, which gave a UI the conversation live. Live progress while the agent works is needed but not now (see [ideas.md](ideas.md)). *Superseded in part 2026-11-14:* an app reads and writes data the agent owns, so answering by publishing holds only until that exists.

## 2026-11-12

Made in [JEN-19](https://linear.app/reveer/issue/JEN-19), aligning on its proposal. The proposal and design are in `openspec/changes/archive/2026-11-12-add-file-tools/`:

- **Agents get generic file tools, the same for every model: a ranged read, a whole-file write and an exact string replace.** They're plain function tools on a runtime route that moves a file's bytes as the agent, in its workspace. *Why:* set by the maintainer. jen is model-agnostic, so whatever model is selected, through its adapter, must work well. Exact string replace is the edit shape most widely used across model families. An adapter belongs to an API, not a model family: the Responses adapter reaches any model through OpenRouter. *Rejected:* providers' own tools, such as OpenAI's built-in `apply_patch` and Anthropic's text editor tool, wrapped by each adapter. Each is trained into its own vendor's models only, so the adapter would choose tools by model name and still need generic ones for every other model. Revisit only if the behavior check shows a model editing badly with the generic tools.

Made in [JEN-19](https://linear.app/reveer/issue/JEN-19), reviewing its design:

- **A tool behaves the way established tools of its kind do, and a check adapts to the tool, not the reverse.** The file tools follow the exact-replace convention that Claude Code, Gemini CLI and Anthropic's text editor tool share: a missing file is an error, each line is cut past 2000 characters, and an edit returns its numbered lines. The behavior check stops counting a `read_file` of a missing file as a fault. *Why:* set by the maintainer. The point of generic tools is that a model meets what it expects, and a tool reshaped to pass jen's own check stops being that. *Rejected:* answering a missing file as a result so the check's rule could stay whole, and Claude Code's read-before-edit guard, which is its own convention, not a shared one.

## 2026-11-11

Made in [JEN-20](https://linear.app/reveer/issue/JEN-20), aligning on its proposal. The proposal and design are in `openspec/changes/archive/2026-11-12-add-agent-workspace/`:

- **An agent's commands run in a workspace container beside its own, which the runtime creates and is the only way into.** The workspace container gets the workspace volume and nothing of the agent's: no state, no settings, no network, and limits of its own. *Why:* set by the maintainer. What a command can reach is fixed by what its container is given, on any kernel Docker runs on. *Rejected:* bubblewrap inside the agent's container, which needs Docker's seccomp profile and masked paths loosened. Landlock inside the agent's container, which is rules over a filesystem the command shares: before its version 3 (Linux 6.2) a command emptied `agent.db` with `truncate()`, and the command shares the agent's memory and CPU. Both were measured on Docker Desktop on 2026-11-11. Nesting a container inside the agent's has the same problem as bubblewrap.
- **The workspace follows what's done to its agent, not what happens to its process.** Stopping the agent removes the workspace container and keeps its files. A crash of the agent's process leaves it running. *Why:* set by the maintainer. A crash is jen's failure, not the work's, and the runtime acts on a crash only once the restarts run out, when the agent counts as stopped and its workspace container is removed as a stop would.
- **One `workspace` grant covers the workspace and every tool in it.** *Why:* set by the maintainer. No agent needs commands without files or the reverse yet, and the grant can be split later.
- **The workspace has no network.** *Why:* set by the maintainer. Nothing done so far needs it, and an online workspace would hold the owner's data, content that can carry instructions, and a way to send data out. Package installs are an idea in [ideas.md](ideas.md). *Supersedes in part* 2026-11-10's "agents lose internet access": commands lose it in JEN-20, and [JEN-21](https://linear.app/reveer/issue/JEN-21) cuts off the agent's own container.
- **Tools ship in the workspace image, and the agent's image stays only jen's code.** *Supersedes in part* 2026-11-03's "an agent's image grows with the tools that make it that agent."
- **A command's timeout is the agent's to set, up to a fixed 10 minutes, with background processes left to the shell and output capped.** The default is 2 minutes. When output is cut, the whole of it is saved to a file in the workspace. *Why:* set by the maintainer. A plain message waits for the tool call in progress, so a long command holds the agent's turn. Models already background work with `&`. Output stays in the conversation and is sent again with every later model call, and a command can't always be run twice to see what was cut.
- **A command can write to the workspace's home, `/tmp` and Docker's `/dev/shm`, and nowhere else.** `/dev/shm` is a private 64 MiB `noexec` tmpfs that counts toward the workspace's memory and goes with its container. *Why:* set by the maintainer in the design review. Python's `multiprocessing` keeps its locks there, and without it a `Pool` fails, measured. *Rejected:* `IpcMode: none`, which mounts no `/dev/shm`.

Made in [JEN-20](https://linear.app/reveer/issue/JEN-20), verifying its implementation:

- **The behavior check's delegation tasks may fail a run or two on `openai/gpt-6-luna`, and that doesn't hold back a change.** *Why:* set by the maintainer. Three runs of the check on `main` failed 0, 2 and 1 of their 18 runs, with the same faults this branch showed, so the check's all-pass bar fails without any change. A change is held to its own task passing and to delegation failing no worse than `main`'s. The faults seen are listed in [environment.md](environment.md).

## 2026-11-10

- **A design isn't shaped around what jen lacks.** What the right design depends on becomes its own task. Set by the maintainer while aligning [JEN-18](https://linear.app/reveer/issue/JEN-18)'s proposal, which split out [JEN-19](https://linear.app/reveer/issue/JEN-19) to give agents file tools. See [conventions.md](conventions.md). *Why:* twice in one discussion, a missing feature (skills and sub-agents that write UI, then file tools) pulled the UI engine's design toward a weaker shape.

- **An agent's workspace is a milestone of its own, Agent workspace, and commands come before files.** [JEN-20](https://linear.app/reveer/issue/JEN-20) lets agents run commands and sets the workspace's boundary: what a command can and can't reach. [JEN-19](https://linear.app/reveer/issue/JEN-19)'s file tools run inside that boundary and add none of their own. The milestone has no "Design and scope" issue, because it was scoped in the discussion that split it out. *Why:* set by the maintainer. A workspace is needed whatever an agent's UI is. Once commands exist, they can reach anything the agent's user can, so confining the file tools to a folder would protect nothing. The real boundary has to hold for commands, and file tools are a convenience inside it.
- **The runtime keeps the model key and proxies agents' model calls, and agents lose internet access.** It's [JEN-21](https://linear.app/reveer/issue/JEN-21), the Agent workspace milestone's last task. *Completed 2026-11-16* by JEN-21 (see 2026-11-16). *Why:* set by the maintainer. An agent that runs commands can read any secret in its environment and send it anywhere. It comes last because no other task's design depends on it, and jen has no users, so until then only the maintainer's own runs are exposed. *Superseded in part 2026-11-11:* commands run in an offline workspace from JEN-20 on, and JEN-21 cuts off the agent's own container (see 2026-11-11).

Made in [JEN-3](https://linear.app/reveer/issue/JEN-3), designing the UI engine and scoping its milestone into [JEN-18](https://linear.app/reveer/issue/JEN-18):

- **Each agent writes its own UI as code, in HTML, CSS and JavaScript.** jen supplies no component catalog and no model that turns data into UI. *Why:* set by the maintainer. jen decides as little as possible and lets agents do the coding, because it's built for tomorrow's models. A catalog caps what an agent can draw at what jen designed, however good models get. A separate model that presents the agent's data is a design decision made for the agent. HTML is what models have seen most, runs on every device with a browser or web view, and comes with the browser's sandbox. *Rejected:* a declarative catalog such as Google's A2UI (v0.9.1), where the screen draws the agent's description with its own components. Also native toolkits, which need one language per platform and a build step.
- **The UI engine lives in the agent, and every agent presents itself, sub-agents included.** Agents whose displays are related, such as a project manager's dashboard and its engineer sub-agent's, are related through the tree. *Why:* set by the maintainer. jen isn't an app built to serve agents (see [product.md](product.md)), and a UI engine on top of jen would be one.
- **Interfaces are dumb: no control acts on its own.** An interaction reaches the agent as a message, delivered like any other, with whatever context the agent attached to the control. The agent acts on it and updates its UI, and the open page shows the update. *Why:* set by the maintainer. Behavior stays in the model, and the UI can do nothing the agent couldn't be asked to do in a message. *Superseded in part 2026-11-14:* an app runs logic the agent wrote and moves data without a model turn. A message to the agent still needs a person to have acted.
- **The agent's UI runs in a sandboxed frame inside a fixed page the agent serves.** The frame has no network, and its only way out is an action handed to the page. The page is jen's code. It holds the connection to the agent and the viewer's token, passes actions out and swaps new versions in. *Why:* a browser isolates code only at a frame boundary. In one document the model's code would run beside the viewer's token, and "dumb" would rest on trusting what the model wrote. The sandbox is the one part of the UI engine enforced in code.
- **The agent keeps its latest UI in `/state`, and opening it shows that version at once.** The agent decides when to rewrite it. *Why:* a new UI on every open isn't automatically good. People build familiarity, and the fastest UI is one that isn't generated.
- **The runtime gets no UI role of its own.** It relays an agent's UI and the actions sent to it the way it relays messages and events, and who may open an agent's UI follows who may reach it. JEN-18 adds the UI's routes to the relay, which today passes only `/messages` and `/events`. In this milestone a browser reaches an agent's UI only locally. Real auth stays with [JEN-4](https://linear.app/reveer/issue/JEN-4). *Moved 2026-11-16:* real auth waits for hosting, after this project. *Why:* every request to an agent already goes through the runtime's relay, which checks access where the tree is.
- **The milestone covers one path, for a root agent.** The agent writes its UI, an action reaches it as a message, and its UI updates. Everything else waits, including sub-agents' UIs and knowing the device and situation (see [ideas.md](ideas.md)). Sub-agents' UIs need one more decision first: a sub-agent's final text goes to its parent whoever started its turn, so an owner's click on a sub-agent's UI would send its parent an unasked-for reply. *Why:* set by the maintainer, to keep the milestone small in an area full of new ideas.
- **The requirement to behave on a model of `openai/gpt-6-luna`'s class covers delegation. Whether it covers generative UI isn't decided.** Supersedes in part 2026-11-06. *Why:* set by the maintainer.

## 2026-11-09

Made in [JEN-15](https://linear.app/reveer/issue/JEN-15), building the skills and docs that keep the project understood and maintained:

"Context" also collided with OpenSpec's `context` setting and with context files in general.

Every copy is also one more thing to drift.

- **`docs/` is for understanding, and nothing loads it by default.** Each view names the files it describes, so `tend` can find drift. The interactions view replays recorded runs of the behavior check. *Why:* detail there costs no agent tokens unless it's needed, and a recording can't drift from how agents behave.

Each pass is one Linear issue labeled `tend`, outside cycles, and everything it produces goes in one pull request, with no issue of its own. A pull request of fixes only merges without review. New views, new or changed skills, code cleanups and questions are proposals, and any one of them puts the whole pull request up for the maintainer's review. *Why:* set by the maintainer. Fixes aren't code, and the boundary keeps a silent merge from changing what agents are told to do. One issue per pass keeps upkeep visible in Linear even when it finds nothing, while an issue per finding added nothing the pull request doesn't already carry. *Refined in part 2026-11-16:* an approved proposal that needs a design gets an issue of its own.
- **`tend` changes something only when it can say what's wrong without the change, and an empty pass is the expected result.** *Why:* set by the maintainer. An agent running an upkeep skill will otherwise find something to change.
- **`tend` looks at code only for how it's organized and reads, and only proposes.** Each cleanup is carried out as its own change that alters no requirement or test assertion. Bugs, performance and tests belong to a separate skill. *Why:* the maintainer wants few proposals, each worth a change of its own. Agents also score about 70% on refactorings specified in detail and under 8% on open-ended cleanup ([CodeTaste](https://arxiv.org/pdf/2603.04177)).

## 2026-11-07

Made in [JEN-12](https://linear.app/reveer/issue/JEN-12), designing `add-replies-and-wait`. Details are in its design, decisions 3, 5 and 6:

- **An agent is shown no agent ID it can't message.** It isn't told its own ID or its parent's. Its parent's messages carry no sender line, and tool results leave out the parent field. *Why:* while Luna knew an address for its parent, it sometimes answered with the send tool. Hiding the address took that to 0 of 36 lab runs. Constraining the tool's schema instead only redirected the mistake.
- **`wait` stays, with no `working` flag and no update messages.** *Why:* the lab tested ending the turn to wait, with replies flagged as still working. Agents then did delegated work themselves or re-asked sub-agents still doing it, and only 25 of 36 runs were clean, against 34 of 36 with `wait`. An open `wait` already shows that an agent is still working.
- **An agent that owes a reply and ends its turn empty sends an empty reply, and only `wait` shows it.** It clears the agent's debt and never wakes the parent by itself. The parent's next `wait` shows it as `From: a1` with nothing under it, and one still pending when the parent ends its turn is dropped. *Why:* the maintainer rejected an artificial reply text, and a status line in the runtime's words. In the lab, a fixed text drew extra owner replies, and an empty message delivered like any other woke the parent after every thank-you. A bare `From:` line in a `wait` result was enough for parents to ask again for a missing result.
- **A sub-agent that stops for good is its parent's to handle.** The runtime's message about it wakes the parent. The parent restarts it, or deletes it and does without it, and stopping or deleting clears what it owes. The runtime doesn't change. *Why:* set by the maintainer. The runtime's message is enough for the model to act on, and a check against the runtime would be a second record.

Made in [JEN-12](https://linear.app/reveer/issue/JEN-12), aligning on its proposal. The proposal and design are in `openspec/changes/archive/2026-11-08-add-replies-and-wait/`:

- **jen's agents must behave on a model of `openai/gpt-6-luna`'s class.** *Why:* set by the maintainer. ## 2026-11-04

Made in [JEN-11](https://linear.app/reveer/issue/JEN-11), after the maintainer asked that every real interaction between parent and child hold up. Details are in `openspec/changes/archive/2026-11-05-add-agent-delegation/design.md`, decisions 3, 4 and 8:

- **Three ways to reach a busy agent.** A plain message waits for the batch of tool calls in progress and reaches the model before its next call. An urgent message cancels the call in flight, skips the rest of the batch and reaches the model at once. Stop and delete halt the agent's whole subtree. *Superseded in part 2026-11-06:* a child no longer sends its parent anything, urgent or not. It answers by ending its turn (see 2026-11-06). Anyone who may message an agent may send it an urgent message, a child to its parent included. *Why:* stopping an agent to correct it froze its whole subtree, and after a restart its sub-agents stayed stopped. A plain message that cut every batch short made routine news cost a re-plan. A cancel leaves the conversation as crash recovery does, so it adds no new state.
- **The runtime sends messages as `runtime`, only for facts it witnessed.** It reports a sub-agent whose restarts ran out to its parent, and tells an agent that's started again which of its sub-agents are still stopped. They're ordinary messages through the inbox, with no new route, event or item type. *Why:* in both cases a parent would otherwise wait forever, and only the runtime saw what happened.
- **A child that goes idle without reporting stays a known risk.** It's covered by the instructions, and the live check measures it. *Why:* nothing failed, so any coded fix would be code judging what the model should have done. A follow-up tool that wakes a parent is the fix if it proves real.

## 2026-11-03

Made in [JEN-11](https://linear.app/reveer/issue/JEN-11), aligning on how agents delegate. The proposal and design are in `openspec/changes/archive/2026-11-05-add-agent-delegation/`:

- **Delegation is modelled on people working together, without people's limits.** A parent can interrupt a child, a child can ask its parent a question, and both carry on afterwards. An agent can answer and keep working in the same breath. *Why:* set by the maintainer. One mechanism should support any scenario rather than one feature per scenario.
- **The user is the root agent's parent and nothing more.** The owner's ID is `owner`, and everyone is addressed by ID. *Why:* interrupting or asking works the same in every direction, the user included.
- **Every agent has a durable inbox, and sending never waits for a reply.** A message reaches the agent at its next step, between one model or tool call and the next, and its model decides what the message means. Agents talk only by sending, and their text output reaches only watchers of their stream. *Why:* a blocking ask can deadlock two agents. Replaces JEN-9's `409` (see 2026-10-28). *Superseded in part 2026-11-04:* when a message arrives, and the reliance on stop and delete for emergencies (see 2026-11-04). *Superseded in part 2026-11-06:* agents send only downward, and a turn's final text is the reply to the agent's parent (see 2026-11-06).
- **Messages between parent and child are delivered right away, not held as mail.** *Why:* a sub-agent is an extension of its parent's work. If a child talks too much, its parent tells it to talk less. Mail is kept in [ideas.md](ideas.md).
- **A message to a stopped agent starts it.** Sleeping and being stopped are the same. *Why:* a sleeping parent costs nothing, and a parent that wants a child to stay stopped doesn't message it.
- **Every step is saved as it happens, and an interrupted turn resumes from its last saved step.** *Why:* agents carry on after a crash or stop, and a finished step such as a spawn is never repeated. A failed turn now keeps the steps it finished, which supersedes JEN-9's promise that it sends nothing.
- **An agent knows its own grant and offers only the tools it allows.** *Why:* a tool the runtime will always refuse only wastes the model's calls.

Made in [JEN-10](https://linear.app/reveer/issue/JEN-10), before it merged:

- **The runtime and the agent have separate images, built from one `Dockerfile`.** The `agent` target, `jen-agent`, holds only `src/agent/`. The `runtime` target, `jen-runtime`, holds only `src/runtime/`, with no dependencies, no volume and no user, so it runs as root. The runtime starts agents from `JEN_AGENT_IMAGE` (default `jen-agent`). *Why:* the two share no code and will diverge. An agent's image grows with the tools that make it that agent (*superseded in part 2026-11-11:* tools ship in the workspace image), while the runtime, the one container with root on its host, should carry as little as possible. An agent can't read the runtime's code, and the runtime has no `/state` volume to clean up. One `Dockerfile` keeps both on one base. `src/` has one directory per image, so the agent's whole code (entrypoint, protocol server, turn loop, store, model adapters) sits in `src/agent/` and the layout shows the split.

## 2026-11-02

Made in [JEN-10](https://linear.app/reveer/issue/JEN-10), building the agent runtime. Its requirements are in `openspec/specs/agent-runtime/`, and the design document in `openspec/changes/archive/2026-11-03-add-agent-runtime/`:

- **The runtime runs as a container beside its Docker engine, and reaches it only through the engine's socket.** Deploying jen anywhere, a cloud VM included, means running that container there. *Superseded 2026-11-03:* it was the agent's image with the command `src/runtime/main.ts`; it now has an image of its own (see 2026-11-03). There is no abstraction over where agents run. Stronger isolation such as gVisor or Kata plugs in as a Docker runtime. *Why:* on Docker Desktop a host process can't reach containers on a Docker network, while a container reaches its agents by name on every platform. Docker covers every deployment we have.
- **Docker labels are the only record of the tree.** An agent is a labelled volume (its ID, parent and grant), and each run of it is a container. The runtime keeps no state and reads the tree back from the engine on startup, repairing what a crash left half done. *Why:* a second record, such as a database in the runtime, could disagree with Docker after a crash.
- **Every request to an agent is relayed through the runtime.** No agent's port is published. *Why:* it's the only design that lets an owner reach a root agent on a remote VM or on Docker Desktop. It also keeps agents' protocol tokens inside the runtime, and puts the check of who may reach whom where the tree is.
- **An owner token plus one token per agent.** `JEN_OWNER_TOKEN` identifies the owner. Each agent gets a new random `JEN_TOKEN` every time it starts, which the runtime presents when relaying and the agent presents to identify itself. A caller acts only on its own descendants. *Why:* one shared token would let any agent act as any other, which makes narrowing meaningless.
- **`spawn` is the only capability until a model proxy exists.** Every agent gets the owner's model settings. The tree is bounded by depth (default 3) and by count (default 10), and stopped agents count. *Why:* model access as a yes-or-no switch would only produce agents that can't run, and a raw API key can't be narrowed (see the model-access question in [plan.md](plan.md)).
- **A deliberate stop or delete cascades, and a crash doesn't.** A crashed agent is restarted by Docker's `on-failure` policy, at most 3 times, keeping its token, state and place in the tree, and its sub-agents keep running. *Why:* tying a sub-agent's life to its parent's process is what the 2026-11-01 decision ruled out, and a restart policy needs no watcher.
- **One runtime per name on an engine.** Each runtime claims the container name `<name>-runtime`, and a second one exits. *Why:* the runtime orders operations only within its own process, and container names are an atomic lock the engine already provides.
- **Spawn and start answer once the agent accepts connections**, waiting at most 30 seconds. Found by the live check and chosen by the maintainer during implementation. *Why:* `running` should mean reachable. Without the wait, a relay sent straight after got `502`, and an agent that never boots would show as running.

- **A task's pull request opens as a draft once its design is written.** Set by the maintainer during [JEN-10](https://linear.app/reveer/issue/JEN-10). It's marked ready for review when implementation is done. *Why:* review comments on the proposal and design are easier inline on a pull request than in chat. See [conventions.md](conventions.md).

Design beyond the split belongs to the person doing each task.

Made in [JEN-7](https://linear.app/reveer/issue/JEN-7), building the agent loop and model port. The full design is in `openspec/specs/` (capabilities `agent-loop`, `model-port` and `openai-responses-adapter`):

- **jen keeps the conversation, and never relies on the provider keeping it.** Every model call sends the whole conversation. The Responses adapter sets `store: false`, which turns off OpenAI's stored response state, and never refers to a stored response or item. That isn't a retention guarantee: what a provider keeps otherwise, such as OpenAI's abuse-monitoring logs, depends on its policies and the account's data controls. *Why:* jen can then change model or provider partway through a conversation, and any agent can read it. Provider-side state exists only on OpenAI, and jen would still need its own copy for every other API.
- **The model port is request/response, with no streaming yet.** *Why:* nothing reads a partial turn until the UI engine ([JEN-3](https://linear.app/reveer/issue/JEN-3)). Streaming is added then.
- **The port and the loop carry only what something uses.** System instructions, token usage, cancellation, typed model errors, reasoning across turns and a step limit are each added when a caller needs them. *Why:* every field added speculatively is one each future adapter has to map, and guessing ahead is how a port ends up copying one vendor's shape.
- **TypeScript runs directly on Node 26, with no build output.** `tsc --noEmit` is the build, and `erasableSyntaxOnly` keeps the code to what Node can strip. *Why:* nothing consumes emitted JavaScript yet. It can be added later as a second auth option on the adapter, with no change to the port.

- **Virtually all feature work goes through OpenSpec, and the proposal is aligned on before anything else.** Set by the maintainer at the start of [JEN-7](https://linear.app/reveer/issue/JEN-7). *Why:* the proposal is where agent and maintainer agree on what's being built before design and code commit to it. Made in [JEN-1](https://linear.app/reveer/issue/JEN-1), designing the jen agent:

- **A point is about 4 hours of the maintainer's time, and capacity is about 8–9 points a week.** *Why:* agents write nearly all the code, so the scarce resource is the maintainer's time, not the coding. Estimating that resource is what makes cycle planning honest. See [conventions.md](conventions.md).
- **A jen agent is written in TypeScript on Node.** *Why:* the agents are the UI, and generated UI will almost certainly be web tech, so one language runs from the agent to the renderer. The strongest model-client options and npm distribution are TypeScript-native too.
- **jen builds its own agent loop. No third-party agent SDK.** *Why:* the harness is jen's product. Delegation and self-presentation have to be native to the loop, not fitted around another SDK's shape. A *model* SDK underneath is fine.
- **Model access goes through a port that jen defines, with adapters behind it** (ports and adapters, also called hexagonal architecture). The port states what jen needs in jen's own terms. Only an adapter imports a model SDK, and no SDK type crosses the port. The first adapter wraps the official **OpenAI SDK** and targets the **Responses API**. It reaches OpenAI directly, and open models and Claude through OpenRouter's Responses endpoint, which translates for every model it hosts (beta as of this date). A second adapter on the same SDK targets **Chat Completions**, for endpoints that speak only that (Gemini, Mistral, DeepSeek, local servers and others). A native **Anthropic SDK** adapter comes after that. The second implementation from day one is a scripted fake model, which is also the loop's test fixture. No provider registry, config-driven adapter selection or plugin system until a real case needs one. *Why:* jen must never be tangled with a model SDK, so SDKs can be swapped or added. The official SDKs are closest to the source, because each vendor maintains its own and tracks its API. The main risk is a port that quietly copies the OpenAI SDK's shape. The fake catches the obvious cases, two adapters for two APIs of one SDK catch more, and the Anthropic adapter is the real test. Responses goes first because it's OpenAI's current API, carries reasoning across turns for OpenAI's reasoning models, and is where compatible endpoints are heading.
  - *Rejected:* pi-ai (`@earendil-works/pi-ai`). It's a good, lightweight multi-provider client, but it normalizes over the official SDKs. Behind jen's port it would be a wrapper inside a wrapper, and it pins SDK versions behind current: Anthropic 0.129 against 1.3.0 as of this date. Also rejected: the Vercel AI SDK, whose Agent and UI-streaming layers lean into ground jen means to own, and TanStack AI, which is a framework rather than a client and reached 1.0 on 2026-10-22.
- **Each jen agent is an OCI container** with its own filesystem, a mounted volume for state that outlives the container, and **SQLite** on that volume as its database. Isolation strength (plain Docker, gVisor, microVMs) is a deployment setting, because the same image runs under all of them. *Why:* cloud, cloud-less and local targets all run Linux containers. SQLite runs in-process and an agent's database has one owner, so it's the fastest fit. Revisit it only if a concrete workload outgrows it.
- **One protocol covers user→agent, agent→agent and parent→child.** Agents talk over the network, never through a shared host. A parent's authority over a child (spawn, stop, inspect) is a permission and a runtime operation, not a second protocol. *Why:* a sub-agent is a jen agent, so peers and children differ in authority, not in wire format. Talking over the network keeps local and remote agents identical, so delegation ([JEN-2](https://linear.app/reveer/issue/JEN-2)) and hosting ([JEN-4](https://linear.app/reveer/issue/JEN-4)) don't force a redesign.

- **The first project is "Agent harness & UI engine"**, with four milestones in this order: Agent container, Agent delegation, UI engine, Distribution and hosting. *Why:* a project is a bounded effort, and the team already stands for the product. Delegation is its own milestone because a sub-agent is the same kind of agent; what's new is the relationship between agents. The UI engine comes before hosting because it's how a user uses jen at all. Local use falls out of building it, and hosting is mostly a question of transport.
- **Target date 2026-11-29, with one milestone per one-week cycle.** *Why:* that's about a week per milestone, plus a slack week. It errs on the safe side and can be pulled in.
- **Milestones get no separate target dates.** *Why:* a milestone's size isn't known until its design issue is done.
- **Each milestone is scoped by its own opening issue**, not in an up-front scoping session. *Why:* scoping before getting into the problem has gone wrong before.
