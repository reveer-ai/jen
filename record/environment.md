# Environment

## Project

- **Repo:** `reveer-ai/jen` on GitHub.
- **Linear:** workspace `reveer`. The `jen` team (key `JEN`) is the product. Linear's GitHub integration has been connected to `reveer-ai` since 2026-10-24. It links a PR to an issue automatically when the issue ID appears in the branch name or the PR title, so don't attach PRs by hand.
- **OpenSpec** 1.15.0, initialized for Claude Code and Codex with the `spec-driven` schema. Its config is in `openspec/config.yaml`. Its skills live in `.claude/skills/` and `.agents/skills/`, and its `/opsx:*` commands in `.claude/commands/opsx/`. All of these are generated, so refresh them with `openspec update` rather than editing them by hand.

## Code

One npm package (ESM, Node ≥ 26) at the repo root. Node runs the TypeScript in `src/` directly, so there's no build output. Unit tests sit next to the code as `*.test.ts`. Live checks against real models are `*.live.test.ts`.

`src/` holds one directory per image, and nothing else:

- `src/agent/`: the agent, everything that runs in an agent's container.
  - `main.ts`: its entrypoint. It serves the protocol on port 8080. The container is the only supported way to run it.
  - `server.ts`: the agent's protocol over HTTP: `POST /messages` into the inbox, the `GET /events` stream, `GET /page` and `GET /ui`, and the bearer token.
  - `loop.ts`: the agent's loop, one saved step at a time: settle the outstanding tool calls, deliver the inbox, call the model. A turn's final text is the agent's reply to its parent, posted from an outbox, and the loop answers a `wait` call from the inbox. It reads all its state from `store.ts`, the conversation, inbox, outbox and the sub-agents that owe a reply in SQLite, so a restart resumes where it stopped.
  - `delegation.ts`: the agent's identity from its environment, the tools its grant allows (with `spawn`, `message_sub_agent` and the tools that manage sub-agents, and with `workspace`, the four in `workspace.ts`, and for a root with `workspace`, `publish_ui` in `ui.ts`), the delegation tools themselves, which call the runtime's API, and the system instructions.
  - `workspace.ts`: the workspace tools, which refuse before sending what the runtime would refuse, such as a command over 64 KiB or content over 16 MiB. `run_command` runs a bash command in the agent's workspace through the runtime's `POST /workspace/commands`. `read_file` returns a text file's lines numbered as `cat -n` does, at most 2000 lines and 32 KiB a call with a note saying where to read on, each line cut at 2000 characters. `write_file` writes a whole file as UTF-8, creating its folders. `edit_file` replaces an exact string, once unless `replace_all` is set, and fails saying why when it doesn't match or matches more than once. The file tools read and write through `/workspace/files`, by `RuntimeClient.readFile` and `writeFile` in `delegation.ts`.
  - `ui.ts`: `publish_ui`, offered only to a root with `workspace`. It reads `ui/index.html` from the workspace through `RuntimeClient.readFile` and saves it unchanged as the next UI version in the store, which keeps only the latest, refusing a file that's missing, isn't UTF-8 or is over 4 MiB.
  - `ui/`: the HTML the agent serves. `page.html` is jen's fixed page, which holds the viewer's token and runs the published UI in a sandboxed `srcdoc` frame with no network, behind the bridge that defines `jen.act` and `jen.version`. `textbox.html` is the UI every agent serves as version 0 until it publishes.
  - `model/`: the model port (`port.ts`), the scripted fake (`scripted.ts`) and the adapters.

  `src/agent/AGENTS.md` holds rules for working in this directory. Codex reads it only when started inside it, so read it yourself before changing code here.
- `src/runtime/`: the runtime, which starts, stops and deletes agents on its Docker engine, relays every request to them, wakes a stopped agent for a message, and reports what only it saw. `docker.ts` is a minimal Engine API client over the socket, `runtime.ts` the tree (its only record is Docker labels), `server.ts` the API and relay, and `main.ts` its entrypoint. Unit tests run against the in-memory engine in `fake-docker.ts`.

`docs/` holds views of how jen works, each a page to open in a browser. Each names the files it describes in a `<meta name="describes">` tag, so `tend` can find a view whose sources changed after it was last edited:

- `architecture.html`: jen's components and how a message flows through them.
- `interactions.html`: real runs of the behavior check replayed step by step, agent by agent. Its runs are in `interactions.data.js`, written by `npm run test:live` with `JEN_LIVE_RECORD=1` set.

Commands:

- `npm run check` typechecks. It's the build, and it rejects syntax Node can't strip, such as `enum`.
- `npm test` runs the unit tests and never the live checks. CI (`.github/workflows/ci.yml`) runs `npm ci`, `check` and `test` on every push and pull request, with no secrets, and the boundary and sandbox checks below.
- `npm run test:live` runs only the live checks. Each but the boundary check skips unless `JEN_LIVE_API_KEY` and `JEN_LIVE_MODEL` are set, either in the environment or in a git-ignored `.env` at the repo root, which only `test:live` loads. Add `JEN_LIVE_BASE_URL=https://openrouter.ai/api/v1` to go through OpenRouter, with a model ID such as `openai/<model>`.
  Known flakes: the agent server's oversized-body test sometimes fails with `EPIPE` or a connection reset ([JEN-14](https://linear.app/reveer/issue/JEN-14)). In a full live run, the runtime check has failed at its deliberate-crash `docker exec` (exit 137) and the container check once timed out waiting for a reply; each passed alone. The behavior check's delegation tasks fail about one run in each pass, on `main` as well (0, 2 and 1 failed runs in three passes on 2026-11-11): a root that messages its parent or a made-up receiver before spawning anything, a mistyped sub-agent ID, a sub-agent reply under 10 characters, or one reply too many. The command task passed 12 of 12 runs, and the files task 3 of 3 on 2026-11-12, with 1 delegation run failing in that pass. On 2026-11-13 the files task also failed on Luna passing `run_command` a `timeout` outside 1 to 600 seconds, on `main` (1 of 6 runs) and on JEN-18's branch (3 of 9).
  The container check (`src/agent/container.live.test.ts`) also needs Docker running. With credentials set and no Docker, it fails rather than skips.
  The boundary check (`src/runtime/workspace.live.test.ts`) needs Docker and no credentials, so it never skips: it fails without Docker. It probes what a command in a real workspace can reach, and what the file route can read and write there, and CI runs it alone on every push, in its `boundary` job, which is the only check of the boundary on a plain Linux kernel.
  The sandbox check (`src/agent/sandbox.live.test.ts`) needs no credentials and no Docker, so it never skips, but it needs Playwright's Chromium (`npx playwright install chromium`). It serves the agent's server in-process with a stored UI that tries every way out of its frame, opens the page in headless Chromium, and fails if anything reaches its probe server or the agent beyond the page's own requests, if the frame reads the token, or if an action reaches the inbox without a click. CI runs it alone on every push, in its `sandbox` job. Playwright evaluates with a user gesture, which activates the page for a few seconds, so the check reads neither frame until the actions sent on load have been dropped.
  The UI check (`src/runtime/ui.live.test.ts`) always runs on `openai/gpt-6-sol`, through `JEN_LIVE_API_KEY` and `JEN_LIVE_BASE_URL`, and needs Docker as the container check does. It asks a root in its textbox for a UI with a button that asks for a number, clicks it, and passes when the frame shows a number the agent published after the click. Vitest hides a passing check's console, so add `--silent=false` to see the UIs the agent wrote and its transcript.
  The runtime check (`src/runtime/runtime.live.test.ts`) needs Docker the same way as the container check, and starts its own runtime under a unique `JEN_RUNTIME_NAME`. So does the behavior check (`src/runtime/behavior.live.test.ts`), which runs eight owner tasks three times each on that model, one of them a command whose output is far over the cap and one an edit and a write judged by the files they leave, and fails on any misbehaving run, printing its transcript.
- One `Dockerfile` builds three images: `docker build --target agent -t jen-agent .`, `docker build --target runtime -t jen-runtime .` and `docker build --target workspace -t jen-workspace .`. The agent image holds only `src/agent/`, the runtime image only `src/runtime/`, with no dependencies and no volume, and the workspace image only the tools an agent's commands use, with none of jen's code. jen runs by starting the runtime and spawning agents through it, from `jen-agent`. The runtime needs the engine's socket, which is why its image runs as root, and the owner's token, `JEN_OWNER_TOKEN`. It passes its `JEN_MODEL`, `JEN_API_KEY` and optional `JEN_BASE_URL` to every agent. Pass them by name so they stay off the command line, and publish the port on `127.0.0.1` to keep the runtime local. `docker run -d` prints a container ID even when the runtime exits at once on a missing setting such as an empty `JEN_API_KEY`, so if `curl` can't connect, check `docker logs jen-runtime`:

  ```sh
  export JEN_OWNER_TOKEN=$(openssl rand -hex 32)
  docker run -d --name jen-runtime -v /var/run/docker.sock:/var/run/docker.sock -p 127.0.0.1:8080:8080 -e JEN_OWNER_TOKEN -e JEN_MODEL -e JEN_API_KEY -e JEN_BASE_URL jen-runtime
  curl -H "Authorization: Bearer $JEN_OWNER_TOKEN" -d '{"grant":{"spawn":true}}' localhost:8080/agents
  export AGENT=<the id it returned>
  curl -H "Authorization: Bearer $JEN_OWNER_TOKEN" -d '{"text":"Remember the word heron."}' localhost:8080/agents/$AGENT/messages
  curl -N -H "Authorization: Bearer $JEN_OWNER_TOKEN" localhost:8080/agents/$AGENT/events
  curl -X POST -H "Authorization: Bearer $JEN_OWNER_TOKEN" localhost:8080/agents/$AGENT/stop
  curl -X DELETE -H "Authorization: Bearer $JEN_OWNER_TOKEN" localhost:8080/agents/$AGENT
  ```

  `POST /agents` answers `201` with `{"id", "parent", "grant", "state"}` once the agent accepts connections. `GET /agents` lists every agent, and `POST /agents/<id>/start` starts a stopped one from its stored conversation. `/messages` and `/events` are relayed to the agent's protocol, with the sender stamped in `Jen-From` (`owner` for the owner). `POST /messages` takes `{"text": "…"}` and an optional `"urgent": true`, starts a stopped agent first, and answers `202` with no body once the message is in the agent's inbox. Replies arrive on `/events`, which streams every saved item as Server-Sent Events as it's saved, resuming after a `Last-Event-ID` header, plus an `error` event for each failed model call. A root agent's reply to the owner is the final text of its turn: an assistant message from a model response with no tool calls. An assistant message followed by a tool call in the same response reaches no one. `POST /workspace/commands` takes `{"command": "…"}` and an optional `"timeout"` from 1 to 600 seconds (default 120), runs the command with bash in the caller's own workspace, and answers `200` with `{"exitCode", "output", "timedOut"}`, plus `"cut"` when the output passed 8 KiB; only an agent with `workspace` may call it. `GET /workspace/files?path=<path>` answers `200` with the file's exact bytes as `application/octet-stream`, and `PUT` with the bytes as its body writes the whole file and answers `204`, both in the caller's own workspace as `agent`, with a relative path relative to `/home/agent`, so they reach exactly what a command can. A file is at most 16 MiB either way (`413`), a missing file is `404`, and anything else the workspace refuses is `400` with its reason, such as `Permission denied`. A write lands on a temporary file renamed over its target, so one cut short leaves the file as it was. Only an agent with `workspace` may call either. `GET /agents/<id>/ui` is relayed like `/events`, answering `{"version", "document"}`, the latest UI or the textbox as version 0, and is refused with `403` unless the agent is a root with `workspace`. `GET /agents/<id>/page` is the one route without a token: it's relayed only to a running root with `workspace`, and gets `404`, `no UI for agent <id>`, for anything else, starting nothing. The owner opens a root's UI in a browser at `http://127.0.0.1:8080/agents/<id>/page#token=$JEN_OWNER_TOKEN`; the page reads the token from the fragment, which never reaches a server. The full API is in `openspec/specs/agent-runtime/spec.md`, `openspec/specs/agent-workspace/spec.md` and `openspec/specs/agent-ui/spec.md`.

  Stopping an agent removes its container and keeps its volume, `jen-agent-<id>`, and for an agent with `workspace` also removes its workspace container, ending every process in it, and keeps the workspace volume, `jen-workspace-<id>`. Starting it again creates both containers anew, so a rebuilt `jen-agent` or `jen-workspace` image reaches an agent only after a stop and start: running containers keep the image they started from, and the files on both volumes carry over. Deleting it removes all of them, and both act on everything under it. `docker rm -f jen-runtime` stops only the runtime: agents keep running, and a runtime started again with the same command reads the tree back from Docker. To remove everything, delete each agent, which removes its workspace too, then the runtime and its network with `docker network rm jen`. Optional settings: `JEN_RUNTIME_NAME` (default `jen`, which prefixes the runtime's container, network and agents), `JEN_AGENT_IMAGE` (default `jen-agent`), `JEN_WORKSPACE_IMAGE` (default `jen-workspace`), `JEN_MAX_DEPTH` (default 3) and `JEN_MAX_AGENTS` (default 10).

## Tool quirks

- **The Linear MCP can't create cycles or change team settings.** Someone has to do that in the Linear UI. For example, the number of upcoming cycles is set under jen team settings → Cycles.
- **Adding an issue to a cycle moves it from Backlog to Todo.**
- **GitHub refuses an approving or changes-requested review from a pull request's author**, and every session acts as the author, so reviews are posted as `COMMENT` with the verdict in the body.
- **`openspec init` deletes OpenSpec's old global Codex prompts** in `~/.codex/prompts/opsx-*.md`. That's outside the repo, and it does it without asking.
