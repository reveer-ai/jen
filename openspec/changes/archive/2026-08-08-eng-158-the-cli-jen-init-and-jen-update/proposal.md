## Why

ENG-156 made jen publishable and declared, as data, which files it owns in a project it governs. Nothing reads that declaration yet: `jen init` and `jen update` both exit 1 with "not implemented yet", so the package can be installed and does nothing. This change is the code that acts on the contract — the point at which jen stops being a repo to fork and becomes a package that adopts a project.

It also absorbs ENG-157, whose manifest, marker merge, and tool table were all removed by ENG-156's design. What survived — copy, scan-for-stamp, delete-unshipped, delegate to OpenSpec — is an internal module with no runnable deliverable, so it belongs to the commands rather than to a task of its own.

## What Changes

- **`jen init` adopts a project.** It writes the payload from `dist/templates/` — root `AGENTS.md` and the six stamped stage skills into `.claude/skills/` — then writes the once-only scaffold, then ensures OpenSpec is initialized. Non-interactive, credential-free, CI-safe, and safe to re-run.
- **`jen update` reconciles one.** It re-applies the payload and then deletes every stamped file absent from what this version ships, leaving unstamped files alone. It does not write the once-only scaffold; that is the sole difference between the two commands.
- **The reconcile rule gets a scan boundary.** `managed-payload` says a file is deleted if and only if it is stamped and absent from the shipped payload. That rule needs a domain, or "scan for stamps" reads as "walk the project." jen SHALL look only inside the target directories its variable sets declare, and only at the depth the set writes — `.claude/skills/<name>/SKILL.md`, nothing deeper and nothing beside it.
- **The once-only scaffold is settled.** `registry.yaml` gets a stub for the `jen:setup` skill (ENG-160) to fill in. `.claude/settings.json` is seeded with the permissions the stages need. Both are **project-owned from the moment they exist** — written when absent, never read, rewritten, or deleted afterward. This closes ENG-156's open question, which recorded `.claude/settings.json` as having no declared owner.
- **`jen init` refuses to adopt a non-empty project.** Adopting a project that already has content is migration, and migration is not in this change. Where the two collide is the **fixed paths**: variable-set members are stamped and self-describing, and scaffold files are only written when absent, so a fixed path is the one category that can silently destroy what a project wrote. Root `AGENTS.md` is the live case — jen owns it wholesale, and a project that already has one loses it. jen cannot detect this on its own, because ENG-156 gave fixed paths no stamp (correctly: they are always written and can never be orphaned, so they are never deletion candidates — but that also leaves jen unable to tell its own `AGENTS.md` from the project's on first contact).

  So `init` compares each fixed path against what it ships and stops if one exists and differs, naming the file and exiting non-zero. `--force` overwrites. `update` is unaffected and still overwrites unconditionally, because a project running `update` has already adopted. The refusal is deliberately the seam a later `jen migrate` plugs into — at which point `init` on a non-empty project routes there instead of stopping.
- **OpenSpec is spawned, not reproduced.** `jen init` resolves the `openspec` binary from jen's own dependency tree and runs `openspec init --tools claude --no-animation --force` in the project when `openspec/` is absent. jen never learns OpenSpec's file list, so OpenSpec's version moves without touching jen's payload. The tool list is fixed at `claude` for v0.1, matching jen's own `.claude`-only payload; OpenSpec's flag already accepts a comma-separated list, so widening it later is a passthrough argument rather than a redesign.
- **OpenSpec has to outlive `init`, and that shapes how jen is adopted.** OpenSpec reaching jen at init time is not the same as reaching the project afterward, and every stage of the workflow runs `openspec` for the life of the project. Installing jen as a project devDependency — `npm i -D @reveer/jen && npx jen init` — is therefore the documented adoption shape: OpenSpec arrives transitively and both versions are pinned in the project's lockfile. Installed any other way (a global install, a bare `npx`), jen and OpenSpec live outside the project and agents fall back to a floating `npx @fission-ai/openspec`, which can drift from the version that wrote the files. `init` checks whether `openspec` resolves from the project once it has finished and reports the exact command when it does not. It checks and reports rather than writing: `package.json` is the most project-owned file there is, and a project with no `package.json` at all — Python, Go, Rust — must not have one created for it.
- **The project's `.gitignore` is not written.** jen only checks that no managed path is ignored and reports it if one is — a managed file inside an ignored path is invisible to review and silently missing from a fresh clone.
- **Neither command prompts, ever**, on any path including failure. Both report what they wrote, what they refreshed, and what they removed.
- **The stale `openspec-integration` requirement is retired.** It requires OpenSpec's skills to be carried in-tree — written when jen was a fork template, and invalidated when ENG-156 deleted those eighteen files and gitignored them. ENG-156 declared no modified capabilities and left it standing, so `openspec/specs/` currently holds two requirements that contradict each other. Delegation replaces vendoring.

Explicitly out of scope: **migrating an existing project** into the workflow, which is its own future command and the reason `init` refuses rather than merges; binding a project to Linear (ENG-160, the `jen:setup` skill, where the Linear MCP already is — the CLI never grows an API client); release automation (ENG-161); and the adoption docs plus the `AGENTS.md` rewrite (ENG-162).

## Capabilities

### New Capabilities

- `project-install`: what `jen init` and `jen update` do to a project — the payload write, the reconcile rule's scan boundary, the once-only scaffold and its ownership, OpenSpec delegation, and the guarantees both commands hold to (idempotent, non-interactive, never writing outside managed paths).

### Modified Capabilities

- `openspec-integration`: the requirement that the repository carry OpenSpec's skills and command wrappers in-tree is replaced by one that obtains them from the declared dependency via `openspec init`. The capability's other two requirements — the ordered artifact progression and the single root `openspec/` directory — are unchanged.
- `managed-payload`: "Root `AGENTS.md` is owned wholesale" currently asserts that jen overwrites the file whenever it writes its payload, on every run. The `init` guard makes that false at adoption time, so the requirement is scoped to runs after adoption — wholesale ownership from `update` onward, with first contact refusing an existing, differing file unless forced. Ownership itself is unchanged; only the moment it begins is stated. Nothing about the stamp, the deletion rule, or variable sets changes.

## Impact

- **Added**: the install/reconcile module under `cli/`, consuming the `PAYLOAD` declaration and the `STAMP` constants already exported by `cli/payload.ts`. Integration tests built on a deliberately messy fixture — a project-authored skill beside managed ones, a hand-edited managed file, a stamped skill this version no longer ships, and a copied skill with its stamp deleted.
- **Modified**: `cli/index.ts` — the two commands stop being stubs; `USAGE` loses the "not implemented yet" text and the paragraph describing this release as payload-declaration-only.
- **Dependencies**: none added to jen. OpenSpec is already a dependency; this change spawns its binary rather than importing it, so no API surface is coupled. Locating that binary is not quite routine — OpenSpec's `exports` map exposes only `"."`, so resolving `@fission-ai/openspec/package.json` fails outright and resolution has to go through the bare specifier and walk up to the package root. Recorded in design, because the obvious first attempt is the one that does not work.
- **Adoption**: jen becomes a project devDependency rather than a global tool, which is what pins OpenSpec's version alongside jen's. ENG-162 documents it and is the first thing to actually exercise it.
- **Blast radius**: this is the first jen code that writes into a directory it does not own. Every guarantee that matters is a negative one — never touching an unstamped file, never writing outside a managed path, never deleting outside a declared target directory — and negatives are only as good as the tests that try to violate them. That is where the fixture's divergence earns its place; jen's own repository never runs `jen init` on itself and is permanently on the easy path.
- **Downstream**: ENG-160 consumes the `registry.yaml` stub this writes and needs its shape to be legible enough to tell filled-in from untouched. ENG-162 performs a real install against these commands and rewrites the `AGENTS.md` they ship. A future migration command inherits the fixed-path guard as its entry point, and inherits the detection problem behind it — deciding whether an existing `AGENTS.md` should be replaced, merged, or left alone is the substance of that command, not a detail it can defer.
- **Known and accepted**: the `AGENTS.md` this installs still describes adoption by forking, which ENG-156 deferred to ENG-162. Until that lands, `jen init` writes a workflow document whose first section contradicts the mechanism that just installed it.
- **Noted, not fixed here**: `repo-scaffold` requires resources to be declared in `registry.yaml`, and jen's own repository has no such file. `jen init` writing a stub into adopters does not resolve that for jen itself.
