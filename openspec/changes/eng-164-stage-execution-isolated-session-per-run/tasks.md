## 1. The role's credentials

- [x] 1.1 Add `cli/github.ts`: the app-installation token client, mirroring `linear.ts`'s shape — a hand-written client over global `fetch` with an injectable transport, reading its inputs from the environment at the point of use, adding no dependency and writing nothing anywhere. Every error path raises; none returns a token-shaped empty value, for the same reason `linear.ts` never returns an empty candidate set.
- [x] 1.2 Read the role-scoped environment and refuse before anything else happens, naming the variable that is absent: `JEN_REPO`, `JEN_GH_APP_ID_<ROLE>`, `JEN_GH_INSTALLATION_<ROLE>`, `JEN_GH_PRIVATE_KEY_<ROLE>` for the run's own role, plus `LINEAR_API_KEY` and `ANTHROPIC_API_KEY`. Only the role named in the run request is read — a run that reached for a second role's variables could hold two identities, and `pipeline-identity` forbids it. This is the tick's refusal shape reused deliberately: fail naming what is missing, before a session starts, not partway through one.
- [x] 1.3 Build the app JWT with `node:crypto`'s RS256 signing, and exchange it for an installation access token. `node:crypto` signs this natively, so the alternative — shelling out to an Actions-provided minter — is a layering error rather than a convenience: it would work under one runner and not the other, and this module cannot tell which one produced its request.
- [x] 1.4 Add `test/github.test.ts`: generate a throwaway key pair in the test and verify the JWT against its public half rather than against a recorded string, exercise the exchange and each of its failure responses through a stub transport, and assert that a missing variable is named in the refusal. Nothing here reaches the network.

## 2. The isolated run directory

- [x] 2.1 Add `cli/exec.ts`: the module that owns everything touching the world — the directory, the clone, the trust entry, the invocation, the outcome, and the signal. It is the first code in the CLI that spawns a process and the first outside `init`/`update` that touches the filesystem, and it exists as a separate module so that the decision path's guard needs no widening.
- [x] 2.2 Create one temporary directory per run holding `repo/` and `config/`, and remove the whole tree when the run ends — by success, by failure, and by termination alike. Cleanup is one recursive delete rather than a list of things to remember, and two runs share no mutable state at all: not a working copy, not a trust store, not a credential.
- [x] 2.3 Clone at the default branch, then `git fetch origin <branch> && git switch <branch>`, falling back to `git switch -c <branch>` where the remote carries no such branch. `git clone --branch <branch>` cannot be used and this is not stylistic: `design-task` runs against a branch that does not exist yet, so a clone insisting on the branch would fail every design dispatch — the pipeline's entry point — before the session could report anything. Place the branch and stop; do not push it, because a branch pushed by the executor is a branch with no commit explaining it.
- [x] 2.4 Keep the clone full rather than shallow. Stages read history — the resume convention has them check commits against completion markers, and `openspec archive` and the deliver stage both work over more than one commit. The cost on a large repository is accepted rather than solved.
- [x] 2.5 Set `user.name` and `user.email` in the clone to the role's app identity (`<app-slug>[bot]` and `<app_id>+<app-slug>[bot]@users.noreply.github.com`), and put the installation token in the clone's remote URL. The token governs what the run may *do* and the git config governs what the history *says* it was; setting only the first leaves commits carrying whatever identity the host machine has, which on a local runner is a person's — and the audit story `pipeline-identity` rests on silently stops being true.
- [x] 2.6 Write `config/.claude.json` carrying `projects[<clone path>].hasTrustDialogAccepted: true`, and point `CLAUDE_CONFIG_DIR` at `config/`. This is the finding the task was opened for: `-p` does not exempt a run from workspace trust, so an untrusted clone runs as though `.claude/settings.json` were empty — on every run, since every clone is a new absolute path.
- [x] 2.7 Test the isolation rather than asserting it: two concurrent runs resolve to different directories and neither can observe the other's; the tree is gone after a successful run, a failed one, and a terminated one; and a branch absent from the remote is created locally and never pushed.

## 3. The invocation

- [x] 3.1 Spawn `claude -p '/<skill> <TASK>'` in `repo/`, with `--permission-mode dontAsk`, `--output-format stream-json --verbose`, `--mcp-config` for the tracker, and stdin redirected from `/dev/null`. The child's environment carries `CLAUDE_CONFIG_DIR` and the role's credentials and nothing of another role's.
- [x] 3.2 Put the prompt positionally last. A variadic flag placed before it consumes it — verified: `--allowedTools X 'prompt'` took the prompt as a tool name — which fails as a confusing session rather than as an argument error.
- [x] 3.3 Redirect stdin from `/dev/null`. Without it the process waits ~3 seconds for input that will never arrive, on every run.
- [x] 3.4 Run non-bare. `--bare` is the documented mode for scripted calls and skips discovery of skills, MCP servers, auto memory, and `CLAUDE.md` — which is the entirety of what jen installs. The clone is a complete installation, so letting discovery find it is both simpler and more faithful than enumerating it by flag.
- [x] 3.5 Use `stream-json` rather than `json`, which is what forces `--verbose` — plain `json` returns only the final result, and the MCP verification the spec requires lives in the `system/init` event's `mcp_server_errors`. Needing the init event is the whole reason for the format.
- [x] 3.6 Settle the `--mcp-config` payload for the tracker under the project's agent credential, taking its token from the environment. The shape is fixed by the spec and the verification in 4.1 is what makes getting it wrong loud rather than silent; the literal JSON is what a live run establishes. Where a live run is not available in this session, land the payload the design implies and leave 6.5's note saying it is unverified.
- [x] 3.7 Settle the prompt form as `/<skill> <TASK>` — the form the proposal and spec both state. Nothing depends on argument substitution, since no stage skill declares an `argument-hint` or templates `$ARGUMENTS`, and both candidate forms put the identifier in the session's context. Whether trailing text arrives as arguments under `-p` is unverified and belongs to ENG-167's real run; record it as such rather than as settled.
- [x] 3.8 Inject the spawn so the executor's tests never start a session, and point them at a stub script emitting canned `stream-json` events. No test spends money or reaches the network.

## 4. The outcome

- [x] 4.1 Read the verdict from three signals and fail on any of them: `mcp_server_errors` non-empty on the `system/init` event, `is_error` true on the final `result` event, a non-zero exit, or the `Ignoring N permissions.allow entries` warning on stderr. Treating any one as sufficient costs nothing — they agree on success, and a disagreement is a failure either way.
- [x] 4.2 Treat the stderr permission warning as a run failure specifically, and not as a warning to pass along. This is the mitigation that makes an undocumented `CLAUDE_CONFIG_DIR` an acceptable dependency: it converts the exact failure this task exists to prevent — permissions silently inert, discovered when a stage is denied its own build halfway through — into a named first-second failure. The check is on the symptom, so it holds whatever the mechanism, and it catches the variable being withdrawn as readily as a misconfigured path.
- [x] 4.3 Capture the outcome for whatever records it: success or failure, `total_cost_usd` and the session id off the result event, and the transcript. Nothing here writes a run record — that is ENG-165's, and this change hands back a value in the same way ENG-163 emitted a request before a consumer existed.
- [x] 4.4 Correct the task description's claim in the code rather than around it: an in-run failure does *not* only print as the result. Verified against 2.1.220, an authentication failure raised both exit 1 and `is_error: true`, so the result is authoritative and the exit status corroborates.
- [x] 4.5 Test each failure signal on its own, including a `system/init` carrying `mcp_server_errors` and a stderr line carrying the permission warning — so both detections are covered by a test rather than by having been thought about.

## 5. Termination

- [x] 5.1 Handle SIGTERM as ordinary operation rather than as a crash path: a cancelled Actions job and a stopping `jen watch` both produce it. Forward it, wait for the session to stop (Claude Code aborts the turn, kills the Bash process tree, runs `SessionEnd` hooks, and exits 143), then remove the run's directory.
- [x] 5.2 Write nothing to the tracker for a terminated session, and do not close its announcement on its behalf. The task is left carrying a `start` with no `end`, which every later tick reads as in flight until a person moves it — that is the specified behaviour, not a gap. Closing it would restore the loop ENG-163 removed when it dropped leases and TTLs, and would put a tracker write outside a stage session, which `task-dispatch` prohibits categorically.
- [x] 5.3 Test that termination leaves no partially cleaned directory and no credential behind, and that nothing on the tracker path is reached.

## 6. Wiring the tick

- [x] 6.1 Give `tick()` a launcher parameter — a function from a run request to an outcome — and pass the real one from `cli.ts`. `run.ts` never imports `exec.ts`. This is dependency inversion for one specific payoff: `test/dispatch.test.ts`'s guard keeps passing *unmodified* and keeps meaning what it meant. Importing directly would force the guard to be relaxed for a transitive import that legitimately writes, and a relaxed guard no longer distinguishes the case it was written to catch.
- [x] 6.2 Decide and report every candidate first, then launch the dispatched ones together and await them. No semaphore is needed: `decide()` already caps the set at `--concurrency`, so anything launching exactly what it emits is capped by construction.
- [x] 6.3 Add `--dry-run` to `cli.ts`, which performs the tick and omits the launcher. Acting is the default and holding back is the flagged case. It must not be a second code path that could decide differently — a preview that does not predict is worse than no preview, because it is trusted.
- [x] 6.4 Exit non-zero when the executor failed, and not when a stage parked a task at `Pending`. Parking is one of the two ways every session is supposed to end; a runner that goes red every time a stage correctly asks for a human trains its operator to ignore it, which is worse than not reporting at all.
- [x] 6.5 Confirm `test/dispatch.test.ts`'s source-level guard over `cli/run.ts`, `cli/linear.ts`, and `cli/stages.ts` passes untouched. If it needs editing, 6.1 was done wrong — the guard is the property, not an obstacle to route around.
- [x] 6.6 Test the wiring with an injected launcher: `--dry-run` launches nothing and reaches the same decisions as a run that acts; a normal invocation launches exactly what it dispatched; and the command waits for its sessions rather than exiting once they are started.
