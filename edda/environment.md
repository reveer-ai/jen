## Code

One npm package (ESM, Node ≥ 26) at the repo root. Node runs the TypeScript in `src/` directly, in a checkout and in the images. Only the published package, `jen-ai`, is built: Node won't strip types under `node_modules`, so `npm run build -- <x.y.z>` (`scripts/build.ts`) compiles `src/cli/` into `dist/` with a `package.json` of its own. Unit tests sit next to the code as `*.test.ts`. Live checks against real models are `*.live.test.ts`.

`src/` holds one directory per image, plus `src/cli/`, which runs on the user's machine, and `src/machine/`, jen's machine for Apple silicon Macs, and nothing else:

- `src/agent/`: the agent, everything that runs in an agent's container.
  - `main.ts`: its entrypoint. It serves the protocol on port 8080. The container is the only supported way to run it.
  - `server.ts`: the agent's protocol over HTTP: `POST /messages` into the inbox, the `GET /events` stream, `GET /page` and `GET /ui`, and the bearer token.
  - `loop.ts`: the agent's loop, one saved step at a time: settle the outstanding tool calls, deliver the inbox, call the model. A turn's final text is the agent's reply to its parent, posted from an outbox, and the loop answers a `wait` call from the inbox. It reads all its state from `store.ts`, the conversation, inbox, outbox and the sub-agents that owe a reply in SQLite, so a restart resumes where it stopped.
  - `delegation.ts`: the agent's identity from its environment, the tools its grant allows (with `spawn`, `message_sub_agent` and the tools that manage sub-agents, and with `workspace`, the four in `workspace.ts`, and for a root with `workspace`, `publish_ui` in `ui.ts`), the delegation tools themselves, which call the runtime's API, and the system instructions.
  - `workspace.ts`: the workspace tools, which refuse before sending what the runtime would refuse, such as a command over 64 KiB or content over 16 MiB. `run_command` runs a bash command in the agent's workspace through the runtime's `POST /workspace/commands`. `read_file` returns a text file's lines numbered as `cat -n` does, at most 2000 lines and 32 KiB a call with a note saying where to read on, each line cut at 2000 characters. `write_file` writes a whole file as UTF-8, creating its folders. `edit_file` replaces an exact string, once unless `replace_all` is set, and fails saying why when it doesn't match or matches more than once. The file tools read and write through `/workspace/files`, by `RuntimeClient.readFile` and `writeFile` in `delegation.ts`.
  - `ui.ts`: `publish_ui`, offered only to a root with `workspace`. It reads `ui/index.html` from the workspace through `RuntimeClient.readFile` and saves it unchanged as the next UI version in the store, which keeps only the latest, refusing a file that's missing, isn't UTF-8 or is over 4 MiB.
  - `ui/`: the HTML the agent serves. `page.html` is jen's fixed page, which holds the viewer's token and runs the published UI in a sandboxed `srcdoc` frame with no network, behind the bridge that defines `jen.ask` and `jen.version`. `textbox.html` is the UI every agent serves as version 0 until it publishes.
  - `model/`: the model port (`port.ts`), the scripted fake (`scripted.ts`) and the adapters.

  `src/agent/AGENTS.md` holds rules for working in this directory. Codex reads it only when started inside it, so read it yourself before changing code here.
- `src/runtime/`: the runtime, which starts, stops and deletes agents on its Docker engine, relays every request to them, wakes a stopped agent for a message, and reports what only it saw. `docker.ts` is a minimal Engine API client over the socket, `runtime.ts` the tree (its only record is Docker labels), `workspace.ts` a workspace's fixed bounds and the bash scripts the runtime sends to run commands and move files, with the parsers for what they print, `server.ts` the API, the relay and the model route, `model.ts` the check every model call passes, and `main.ts` its entrypoint. Unit tests run against the in-memory engine in `fake-docker.ts`.
- `src/cli/`: the `jen` command, run on the user's machine, outside any container, as the owner's client of the runtime's API. It imports only types from `src/runtime/` and `src/agent/`, so none of their code runs there. `jen.ts` is its entry, the package's `bin`, which refuses Node below 26 before importing anything, `release.ts` holds `VERSION`, undefined in a checkout and the release's version in the package, which the build writes, `main.ts` parses the arguments and dispatches, `docker.ts` runs a `docker` command, never the socket: on Linux the user's, so their context and `DOCKER_HOST` hold, and on macOS the platform package's, pointed at jen's machine, `machine.ts`, which starts, stops, upgrades and removes the machine, `settings.ts` keeps the settings in the `<name>-settings` volume, `runtime.ts` starts, replaces and stops the runtime's container, `api.ts` is the API client, `roots.ts` the commands on roots by name, `follow.ts` follows a query to its reply on the root's event stream, `browser.ts` opens a UI and `uninstall.ts` deletes everything of jen's. Unit tests run against the in-memory engine in `fake-docker.ts` and the stand-in API in `fake-runtime.ts`, set up by `harness.ts`.

- `src/machine/`: jen's machine, the Linux VM that is jen's only engine on an Apple silicon Mac, and its launcher. The Dockerfile's `machine` target builds it with `build.sh` from Alpine, Docker's static engine for Linux, the files in `system/` and the initramfs's `init`. The engine's version (`DOCKER_ENGINE` in the `Dockerfile`) and the macOS client's (`DOCKER_CLIENT` in `scripts/machine.ts`) move together, which a test checks, and each pins its download's SHA-256, since Docker publishes none. `check.sh` checks a booted machine from inside, and `NOTICE` is the platform package's. `launcher/` is `jen-machine`, a SwiftPM package: `JenMachine` holds what needs no VM, which `swift test` covers, and `jen-machine` runs the VM. How it all works is in `docs/architecture.html`, and why in the archived `give-jen-its-own-machine` change.

`docs/` holds views of how jen works, each a page to open in a browser. Each names the files it describes in a `<meta name="describes">` tag, so `tend` can find a view whose sources changed after it was last edited:

- `architecture.html`: jen's components and how a message flows through them.
- `interactions.html`: real runs from an evaluation replayed step by step, agent by agent, with a failed run's faults. Its committed runs are in `interactions.data.js`, written by `npm run eval -- record <evaluation>`, and it opens any evaluation's `runs.jsonl` picked from disk. The app's browser pane shows a local page as a snapshot without its data file, so open a `runs.jsonl` there, or open the page in a browser.

- `npm run eval` measures how agents behave on a real model, as each task's pass rate, and compares two builds or two models side by side. Its code is in `scripts/eval/` and its requirements in `openspec/specs/agent-evaluation/spec.md`. It needs Docker and the same `JEN_LIVE_*` variables, from the environment or `.env`. Its options: `--tasks <a,b>` (default every task in `scripts/eval/tasks.ts`), `--runs <n>` per task and side (default 10), `--model <id>`, `--build <ref>` (default the working tree, uncommitted and untracked files included), `--against <ref>` and `--against-model <id>` (either gives a second side), `--prompt <text>` with `--grant <spawn,workspace>`, and `--parallel <n>` (default 24 runs in flight across both sides). Each side builds its own images, tagged `jen-<target>:eval-<id>-<side>`, a ref from a temporary `git worktree`, and runs them under a runtime named `jen-eval-<id>-<side>`, so it touches nothing of the user's jen. It prints each run as it ends and the report at the end, removes everything it started, on Ctrl-C too, and exits 0 whatever the rates. `npm run eval -- report <evaluation>` prints an evaluation's report as Markdown, and `npm run eval -- record <evaluation>` rewrites `docs/interactions.data.js` from it, taking side a's runs first.
  Once its runtimes are up, each evaluation writes `evals/<UTC start>-<id>/` (a build or runtime that fails leaves none): `runs.jsonl`, one line per run with its faults, metrics and transcript, appended as it ends, and `summary.json`, marked partial if interrupted. Tokens come from the runtime's `GET /usage`, the owner's count of each agent's model calls and tokens since the runtime started, deleted agents included, with `cost` when the provider reports one (OpenRouter does). A build without that route reports no tokens. On 2026-11-23, the eight tasks at 20 runs a side on `openai/gpt-6-luna` through OpenRouter took 12 minutes at the default `--parallel`, cost about $0.09 a side, and left a 2 MB folder that gzips to about 160 KB.
- One `Dockerfile` builds three images: `docker build --target agent -t jen-agent .`, `docker build --target runtime -t jen-runtime .` and `docker build --target workspace -t jen-workspace .`. The agent image holds only `src/agent/`, the runtime image only `src/runtime/`, with no dependencies and no volume, both with jen's `LICENSE` and `NOTICE`, and the workspace image only the tools an agent's commands use, with none of jen's code. jen runs by starting the runtime and spawning agents through it, from `jen-agent`. The runtime needs the engine's socket, which is why its image runs as root, and the owner's token, `JEN_OWNER_TOKEN`. Agents' network, named for the runtime, is internal with an isolated gateway, which needs Docker Engine 28.0 or later, and the runtime reaches the provider through the network it was started on.

  For working on the runtime, this is its API, which `jen` drives as the owner. The owner's `POST /agents` takes `{"grant", "name"}` and an agent's only `{"grant"}`. A root's name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter, unique among the runtime's roots (`409` otherwise) and fixed, kept as the `jen.name` label on its volume. `POST /agents` answers `201` with `{"id", "parent", "name", "grant", "state"}` once the agent accepts connections, `name` being null for a sub-agent and for a root made before names. `GET /agents` lists every agent, and `POST /agents/<id>/start` starts a stopped one from its stored conversation. `/messages` and `/events` are relayed to the agent's protocol, with the sender stamped in `Jen-From` (`owner` for the owner). `POST /messages` takes `{"text": "…"}` and an optional `"urgent": true`, starts a stopped agent first, and answers `202` with no body once the message is in the agent's inbox. Replies arrive on `/events`, which streams every saved item as Server-Sent Events as it's saved, resuming after a `Last-Event-ID` header, plus an `error` event, `{"message"}`, for each failed model call, with `"gaveUp": true` for a root's notice that it stopped trying, and a `synced` event, `{"seq": n}`, each time it has sent every item saved so far: when it opens and after each later step, never between one step's items. `n` is the position, the event ID, of the last item it has sent, or 0. A root agent's reply to the owner is the final text of its turn: an assistant message from a model response with no tool calls. An assistant message followed by a tool call in the same response reaches no one. `POST /workspace/commands` takes `{"command": "…"}` and an optional `"timeout"` from 1 to 600 seconds (default 120), runs the command with bash in the caller's own workspace, and answers `200` with `{"exitCode", "output", "timedOut"}`, plus `"cut"` when the output passed 8 KiB; only an agent with `workspace` may call it. `GET /workspace/files?path=<path>` answers `200` with the file's exact bytes as `application/octet-stream`, and `PUT` with the bytes as its body writes the whole file and answers `204`, both in the caller's own workspace as `agent`, with a relative path relative to `/home/agent`, so they reach exactly what a command can. A file is at most 16 MiB either way (`413`), a missing file is `404`, and anything else the workspace refuses is `400` with its reason, such as `Permission denied`. A write lands on a temporary file renamed over its target, so one cut short leaves the file as it was. Only an agent with `workspace` may call either. `GET /agents/<id>/ui` is relayed like `/events`, answering `{"version", "document"}`, the latest UI or the textbox as version 0, and is refused with `403` unless the agent is a root with `workspace`. `POST /model/responses` is an agent's model call, with its own token: the runtime refuses with `400` anything but the request the Responses adapter builds, sets the model to its own `JEN_MODEL`, sends it on with the key and streams the answer back, counting the call and its answer's tokens for the agent. The owner's `GET /usage` answers `{"agents": [{"id", "root", "calls", "inputTokens", "cachedTokens", "outputTokens", "reasoningTokens", "cost"?}]}`, kept in memory since the runtime started, and an agent gets `403`. `GET /agents/<id>/page` is the one route without a token: it's relayed only to a running root with `workspace`, and gets `404`, `no UI for agent <id>`, for anything else, starting nothing. The owner opens a root's UI in a browser at `http://127.0.0.1:8080/agents/<id>/page#token=$JEN_OWNER_TOKEN`; the page reads the token from the fragment, which never reaches a server. The full API is in `openspec/specs/agent-runtime/spec.md`, `openspec/specs/agent-workspace/spec.md` and `openspec/specs/agent-ui/spec.md`.

  Stopping an agent removes its container and keeps its volume, `jen-agent-<id>`, and for an agent with `workspace` also removes its workspace container, ending every process in it, and keeps the workspace volume, `jen-workspace-<id>`. Starting it again creates both containers anew, so a rebuilt `jen-agent` or `jen-workspace` image reaches an agent only after a stop and start: running containers keep the image they started from, and the files on both volumes carry over. Deleting it removes all of them, and both act on everything under it. `docker rm -f jen-runtime` stops only the runtime: agents keep running, and a runtime started again reads the tree back from Docker. `jen uninstall` removes everything of jen's: every container, volume and network labelled `jen.runtime=<name>`, the runtime, the settings, the three images and every version of the registry's that the environment doesn't name others in place of, then the `jen-ai` package when it was installed with `npm install -g`. An installed `jen` pulls its own version's images when they're missing, and after an upgrade removes the registry's other versions, passing over any a container uses. A network created before [JEN-21](https://linear.app/reveer/issue/JEN-21) isn't internal, and a runtime uses the network it finds by its name as it is, so remove an old one by hand: `docker rm -f` the agent and workspace containers on it, which keeps their volumes, then `docker network rm` it, and start the runtime, which creates it anew. Each agent rejoins it at its next start. Optional settings: `JEN_RUNTIME_NAME` (default `jen`, which prefixes the runtime's container, network, agents and settings), `JEN_RUNTIME_IMAGE` (default `jen-runtime` in a checkout and `ghcr.io/reveer-ai/jen-runtime:<version>` installed, read only by `jen`), `JEN_AGENT_IMAGE` (default `jen-agent`, or the registry's), `JEN_WORKSPACE_IMAGE` (default `jen-workspace`, or the registry's), `JEN_MAX_DEPTH` (default 3) and `JEN_MAX_AGENTS` (default 10). `jen` reads the first four from its own environment and passes on the name and the agent and workspace images; the runtime it starts takes the defaults for the last two.

## Releases

Every push to `main` runs `.github/workflows/release.yml`: CI (`ci.yml`, which skips `main` on its own), then `node scripts/release.ts plan`, then the machine, built on arm64 Linux with Docker's client checked, then the images, then on a Mac the launcher and both packages, then the tag and the GitHub release, one run at a time. A release publishes `ghcr.io/reveer-ai/jen-agent`, `jen-runtime` and `jen-workspace` at its version for amd64 and arm64, then `@jen-ai/darwin-arm64`, the platform package, and `jen-ai`, which names it as an optional dependency, to npm through trusted publishing, with no npm token. Nothing is ever released from a laptop, and no release commits to `main`.

- **What ships.** A push releases only when a commit since the last `v<x.y.z>` tag reachable from it changes what's in `SHIPS` in `scripts/release.ts`: `src/` but its tests, `package.json`, `package-lock.json`, the `Dockerfile`, `README.md`, `LICENSE` or `NOTICE`. Otherwise the run's `plan` job says nothing ships. `GITHUB_TOKEN=$(gh auth token) node scripts/release.ts plan` prints what a merge of the current branch would release. Run it in a fresh clone (`gh repo clone reveer-ai/jen`): in the maintainer's clone, its own local `v0.1.0` hides the release's `v0.1.0`, so the plan reads as the first release (seen on 2026-11-20).
- **The version.** The patch number rises, unless a released pull request is labelled `minor` or `major`: label it before merging. The notes are the squash-merged commits' subjects.
- **A failed release** is rerun from GitHub Actions. It pushes the images again, keeps a version npm has from the same commit, and skips a release that exists. A version npm has from another commit fails the run: that takes a run that published but didn't tag, then another merge before the rerun, so rerun promptly. To sort it by hand, create the missing GitHub release on the commit npm names (`npm view jen-ai@<version> gitHead`) with `gh release create v<version> --target <commit>`, and rerun.
- **Standing setup, done on 2026-11-20:** `jen-ai`'s trusted publisher on npmjs.com is `reveer-ai/jen`'s `release.yml`, with no environment and `npm publish` allowed (`npm trust list jen-ai`, which asks for the maintainer's one-time password). The `minor` and `major` labels exist. The `reveer-ai` organization allows public packages, and the three GHCR packages are public, which GitHub can't undo. npm's `0.0.0` is a hand-published placeholder, and `0.0.0-stage` a stub npm made for it.
- **Standing setup for the platform package, done on 2026-11-25** ([JEN-31](https://linear.app/reveer/issue/JEN-31)): the `jen-ai` organization on npm owns the `@jen-ai` scope, apart from the `reveer` organization. `@jen-ai/darwin-arm64`'s `0.0.0` is a hand-published placeholder, and its trusted publisher is `release.yml`, set up as `jen-ai`'s is.
- **Never push the maintainer's local tags `v0.1.0` to `v0.5.0`**, from an earlier jen, or `git push --tags` from that clone: the next release would read `v0.5.0` as the last. Only the release makes tags. Nothing refuses a pushed one, and the `releases` ruleset then refuses deleting it: disable the ruleset, delete the tag, and enable it again.

## The repo

`reveer-ai/jen` is public since [JEN-28](https://linear.app/reveer/issue/JEN-28), under Apache-2.0. Its rulesets are under the repo's Settings → Rules, and `gh api repos/reveer-ai/jen/rulesets` lists them. Rulesets need a public repo on GitHub's Free plan: a private one answers 403.

- **`main`** takes changes only by a squash-merged pull request, once CI's `check`, `boundary` and `sandbox` pass and its review conversations are resolved. CI's `machine` and `launcher` jobs, added by [JEN-31](https://linear.app/reveer/issue/JEN-31), run on every pull request but aren't required checks. A direct push, a force-push and deleting the branch are refused, for everyone, the maintainer included. No approval is required, since GitHub refuses the author's own and the maintainer is the only writer. Merge commits and rebase merging are off in the repo's settings too.
- **When CI itself is broken**, the fix can't pass `check`. Set the `main` ruleset's enforcement to disabled, merge the fix, and set it back to active at once.
- **`v*` tags** can't be moved or deleted: the `releases` ruleset refuses both, for everyone. Creating one isn't refused, since a repository ruleset can't exempt the release workflow's `GITHUB_TOKEN`.
- **Outside pull requests** come from forks. Every workflow run a fork starts waits for the maintainer's approval (Settings → Actions → General), and gets a read-only token and no secrets. Security reports arrive through private vulnerability reporting, under the Security tab.

## Tool quirks

- **`docker build --output <dir>` replaces what's in `<dir>`.** `scripts/machine.ts` exports the `machine` target to a temporary folder and copies its files, so `dist/machine/`'s launcher and `docker` survive a rebuild.

- **`git push` to `origin` can fail with `Permission denied (publickey)`.** The remote is `git@github.com`, but the maintainer's SSH config reaches the `joshtgi` GitHub account only through the host alias `joshtgi`. Push with `git push joshtgi:reveer-ai/jen.git HEAD:refs/heads/<branch>`; `gh` works as it is. Seen on 2026-11-16.
- **The Linear MCP can't create cycles or change team settings.** Someone has to do that in the Linear UI. For example, the number of upcoming cycles is set under jen team settings → Cycles.
- **Adding an issue to a cycle moves it from Backlog to Todo.**
- **`openspec init` deletes OpenSpec's old global Codex prompts** in `~/.codex/prompts/opsx-*.md`. That's outside the repo, and it does it without asking.
