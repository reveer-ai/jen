# Ideas

Ideas the maintainer wants kept, not yet planned or decided. An idea isn't a commitment and doesn't constrain design. When one is scoped into an issue, move it to Linear and delete it here. When one is rejected, delete it and, if the reason matters, log it in [decisions.md](decisions.md).

## Agents

- **Grants that change after spawning, so agents can negotiate them.** *Raised 2026-11-03, in [JEN-11](https://linear.app/reveer/issue/JEN-11).* A sub-agent asks its parent for a capability, such as `spawn`, and the parent's model decides whether to grant it. The negotiation is only messages. What's missing is an operation that changes a grant, open to any ancestor: it widens only as far as the caller's own grant, and narrowing applies to everything under the agent. Grants are stored in labels on agents' volumes, which Docker can't change after creation, so they'd need a record that can change. The agent learns of the change and its tools update at its next step. It would make a good live check, since it exercises messages in both directions, grants and tools that follow the grant.
- **A kernel of its own for each agent's workspace.** *Raised 2026-11-10, in [JEN-20](https://linear.app/reveer/issue/JEN-20).* A container shares its host's kernel, so a single kernel or runc bug lets a command escape. On jen's host, an escape controls the Docker engine and with it every agent and the runtime. A user-space kernel, gVisor (`runsc`, one field in the Engine API's create call), or a microVM per workspace (Kata Containers, Docker Sandboxes) would close that. gVisor runs only on Linux, which on a Mac is jen's machine. There, the machine already confines an escape to its Linux VM, away from the user's Mac, though not from the rest of jen.
- **Workspace processes that outlive an agent's sleep.** *Raised 2026-11-11, in JEN-20.* A stopped agent's workspace container is removed with it, so a dev server or a long build it started dies, though its files are kept. Some work may want to keep running while the agent sleeps, which would mean a workspace whose lifetime is decided apart from its agent's, and that costs something while the agent sleeps.
- **Package installs for an offline workspace.** *Raised 2026-11-11, in JEN-20.* A workspace has no network, so an agent can't `npm install`, `pip install` or `git clone`, and its image is its whole toolset. A proxy in the runtime that lets a workspace reach only package registries would add installs without opening a general way out. Opening the workspace to the internet entirely would put the owner's data, content that can carry instructions, and a way to send data out in one place. Agents need it to build apps with web frameworks and open-source kits (see [decisions.md](decisions.md), 2026-11-14).
- **Models and providers chosen per agent.** *Raised 2026-11-18, in [JEN-25](https://linear.app/reveer/issue/JEN-25).* Today one runtime has one model, endpoint and key, and sets the model on every agent's call (see [decisions.md](decisions.md), 2026-11-16). A model per agent would be part of model access as a grant (see [plan.md](plan.md)'s open questions): chosen when a root is made, passed down like any grant, and checked by the runtime on every call. A key or endpoint per agent goes further: the runtime holds several named providers, and each agent is tied to one, such as a work agent billed to a work key.
- **Mail-style delivery.** *Raised 2026-11-03, in JEN-11.* Messages that wait in an inbox until the receiver chooses to read them, unlike JEN-11's delivery at the next step. Not for parent and child, since a sub-agent is an extension of its parent's work. It fits the later milestone on communication between agents that aren't parent and child (see [plan.md](plan.md)). The inbox is a durable queue either way, so this would add a delivery policy and a tool to read the inbox, not a redesign.

## UI

- **Agents that know their device and situation.** *Raised 2026-11-10, in [JEN-3](https://linear.app/reveer/issue/JEN-3).* An agent writes the best UI for where it's shown, such as a phone, a TV or a laptop, and for the user's situation. The page would send the agent what it knows when the UI is opened and with each action, and the model decides what to do with it. This raises one agent open on several devices at once, and a saved UI for each kind of device.
- **One agent's UI showing its sub-agents'.** *Raised 2026-11-10, in JEN-3.* A project manager's dashboard could embed or link to its engineer sub-agent's display. The sandbox has no network, so embedding needs a way for the page to fetch a sub-agent's UI with the viewer's access.
- **Streaming a UI as it's written**, so the first parts appear while the model is still writing. *Raised 2026-11-10, in JEN-3.*
- **A data layer for agents' apps.** *Raised 2026-11-14, checking [JEN-18](https://linear.app/reveer/issue/JEN-18)'s direction (see [decisions.md](decisions.md)).* Each app's state, owned by its agent. The bridge reads and watches it and writes to it, and the shell checks the viewer's access on every request. The sync behind that delivers changes live, shows a write at once and reconciles it, catches up after a reconnect, resolves concurrent edits without losing one, filters records by access on the server, and migrates data when a publish changes its shape. Every write reaches the agent with its author, and the agent's own filters decide what starts a turn, what's batched and what's only recorded. The agent writes into a running app the same way, which also covers live progress while it works, needed once real tasks run long. Asks from an app become typed events in the protocol, not text the model parses. Open: where the data lives (first guess: each agent's `/state`, reached through the runtime's relay) and how an agent reads its subtree's data.
- **jen's shell, and design passed down the tree.** *Raised 2026-11-14, with the data layer.* The shell grows from JEN-18's page: identity, moving between agents' apps, notifications, perhaps a fixed way to talk to the agent. Stock jen's minimal look, and how an organization's design and code pass down to its sub-agents for reuse. jen's textbox becomes a first screen in the stock look.
- **A conversation pane drawn by jen.** *Raised 2026-11-13, in JEN-18.* A fixed pane beside the agent's UI, plain HTML in jen's page, showing at least what the user said. It would give the user the transcript without generated code, which is why JEN-18 gives a UI no access to the conversation.

## Distribution

- **A release that publishes `jen-ai` only once its platform package installs.** *Raised 2026-11-25, after [JEN-35](https://linear.app/reveer/issue/JEN-35)'s release.* npm makes `@jen-ai/darwin-arm64` installable long after `npm publish` accepts it, with "Your package is being processed": 54 minutes for `0.2.0` and 56 for `0.2.1`, against about 4 for `jen-ai`. Meanwhile `jen-ai@latest` names a version npm answers 404 for, so a Mac install gets `jen-ai` without the machine, since npm skips a missing optional dependency, and `jen` says to reinstall. The release could wait, with a bound, for the registry to serve the platform package before publishing `jen-ai`. Open: what a failed wait leaves behind, and what the delay depends on, such as the package's 112 MB. It matters once jen has Mac users.

## Workflow

- **A view of evaluation results over time.** *Raised 2026-11-23, in [JEN-24](https://linear.app/reveer/issue/JEN-24).* Every evaluation's `summary.json` is committed under `evals/`, each with its build's tree and commit, its model and each task's hash, so the summaries add up to a history of how agents do across jen's versions. A page could chart each task's pass rate, time and tokens by build, starting a new line where a task's hash changed. Nothing reads the history yet but people.
- **The briefing as an OpenSpec artifact.** *Raised 2026-11-09, in [JEN-15](https://linear.app/reveer/issue/JEN-15).* A custom OpenSpec schema could make `deliver-change`'s briefing an artifact of the change, so it's archived in the repo with the change instead of living only in the pull request's description. As of OpenSpec 1.15.0, a schema's artifacts can depend only on other artifacts, and `apply` isn't one. So a `briefing` artifact can be declared, but OpenSpec can't order it after implementation; only a convention or the skill could. `openspec schema fork spec-driven` is the starting point.
- **A skill for uncovering bugs.** *Raised 2026-11-09, in JEN-15.* `tend` looks at code only for how it's organized and reads. Hunting for bugs, flaky tests, failure handling and performance would be a separate skill.
