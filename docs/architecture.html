jen Agent Components

The runtime and the agents it runs, as of JEN-18 (add-agent-ui). See jen Agent Interactions for real runs replayed step by step. One runtime container sits beside the Docker engine and relays every request; each agent is the same image, works one saved step at a time from its SQLite store, and talks to other agents only through the runtime. An agent with the workspace grant also has a workspace: a container of its own with no network, where the runtime runs the agent's commands and reads and writes its files by exec. A root agent with workspace can also publish a UI, which the owner opens in a browser (see below).

A UI, from the agent to the browser and back

  1. A root agent with workspace writes its UI as one self-contained file, ui/index.html in its workspace, with the file tools, and publishes it with publish_ui (ui.ts). The tool reads the file's bytes through the runtime and saves them, unchanged, as the next version in the store, which keeps only the latest. A file that's missing, isn't UTF-8 or is over 4 MiB is refused and nothing changes. Until a first publish the agent serves the textbox shipped in its image (ui/textbox.html) as version 0.
  2. The owner opens /agents/<id>/page#token=<owner token>. It's the one runtime route without a token, relayed only to a running root with workspace; anything else gets the same 404 and nothing starts. The agent serves jen's fixed page (ui/page.html) with a Content Security Policy that lets only the page connect, to its own origin, and frames nothing but its own srcdoc.
  3. The page moves the token from the fragment into sessionStorage, fetches ui (relayed like /events, only for a root with workspace) and streams events with it, reconnecting with Last-Event-ID.
  4. It runs the document in an <iframe sandbox="allow-scripts"> whose srcdoc is a doctype, a policy with no network access, the bridge, and the document as published. The frame has an opaque origin, so it can't read the page or its token, and it reaches no server. The page passes it nothing from the stream.
  5. The bridge defines jen.version and jen.act(context), which hands the page the context and the value of every named input. The page accepts it only from the current frame and version, only while the user's click or key press is still active, and only under the 1 MiB bound, and posts it to messages as UI action on version <n>: and the JSON. It reaches the agent as an ordinary message from the owner.
  6. The agent answers by editing and publishing again. When the stream carries a publish_ui result, the page fetches ui, at most one fetch at a time, and swaps in a new version. The agent's text replies never show on the page; a bar shows only the page's own failures and the agent's error events.

A message, end to end

  1. The owner sends POST /agents/<id>/messages to the runtime with the owner token. An agent messaging a sub-agent does the same through message_sub_agent, with its own token.
  2. The runtime checks the target is the caller's descendant (or parent), starting it first if it's stopped, and relays with the agent's token and Jen-From set to the caller.
  3. The agent's server inserts the message into the inbox and answers 202. Acknowledged means saved. It wakes the loop, or aborts the step in flight if the message is urgent.
  4. The loop settles any outstanding tool calls, delivers the inbox into the conversation in one transaction, and calls the model with its instructions.
  5. The response is saved at once, and every saved item streams out on GET /events through the runtime's relay.
  6. Its tool calls are settled next step: message_sub_agent, spawn_agent and the rest call the runtime, run_command posts to /workspace/commands, which runs the command in the agent's workspace, and read_file, write_file and edit_file get and put the file's raw bytes at /workspace/files?path=, beside it. A wait runs last, and the loop answers it from the inbox once a message arrives or no sub-agent owes a reply; until then the loop stops with the call open.
  7. A response with no tool calls ends the turn, and its text is the reply. A sub-agent's goes into its outbox in the same transaction and is posted to its parent through the runtime. A root's is the assistant message on its stream, where the owner reads it.
  8. With no calls left and an empty inbox, the loop ends. A sub-agent's reply wakes it again.

When things go wrong

  • Restart: all state is in the store, so the loop resumes. A call that may have been running is reported as unknown; later calls in its batch are marked not run. The model decides what to retry.
  • Woken by a message: the runtime starts the agent with JEN_WAKE, which holds the loop until its first message is saved, so recovery never calls the model without it.
  • Model failing: retried after 1, 5 and 25 s, each failure an error event. Then the agent puts a notice in its outbox for its parent (a root shows it on its stream) and waits; any message retries.
  • Runtime notices: the runtime sends as runtime only what it alone saw: a child whose restarts ran out, or sub-agents still stopped when an agent starts.
  • Stop and delete: both act on the whole subtree. Stop removes the agent's container and then its workspace's, ending every process in it, and keeps both volumes; delete removes them too.
  • Workspace: a crash of the agent's process leaves its workspace running. A workspace whose first process dies comes back with its files. When an agent's restarts run out, its workspace container is removed. A file write goes to a temporary file and is renamed over its target only once every byte has arrived, so one cut short leaves the file as it was.
