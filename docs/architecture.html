jen Agent Components

The jen command, the runtime and the agents it runs, as of JEN-31 (give-jen-its-own-machine). See jen Agent Interactions for real runs replayed step by step. The user drives jen with the jen command on their own machine, which keeps its settings in a Docker volume of its own, starts the runtime when a command needs it, and talks to roots by name as the owner. One runtime container sits beside the Docker engine, which on a Mac is jen's own Linux machine (see below), and relays every request; each agent is the same image, works one saved step at a time from its SQLite store, and talks to other agents only through the runtime. Agents' network is internal: an agent reaches the runtime and other agents and nothing else, and calls the model through the runtime, which alone holds the owner's key. An agent with the workspace grant also has a workspace: a container of its own with no network, where the runtime runs the agent's commands and reads and writes its files by exec. A root agent with workspace can also publish a UI, which the owner opens in a browser (see below).

A UI, from the agent to the browser and back

  1. A root agent with workspace writes its UI as one self-contained file, ui/index.html in its workspace, with the file tools, and publishes it with publish_ui (ui.ts). The tool reads the file's bytes through the runtime and saves them, unchanged, as the next version in the store, which keeps only the latest. A file that's missing, isn't UTF-8 or is over 4 MiB is refused and nothing changes. Until a first publish the agent serves the textbox shipped in its image (ui/textbox.html) as version 0.
  2. jen @<name> open starts the root if it's stopped, prints /agents/<id>/page#token=<owner token> on the runtime's port, and opens it in the browser where the system can. It's the one runtime route without a token, relayed only to a running root with workspace; anything else gets the same 404 and nothing starts. The agent serves jen's fixed page (ui/page.html) with a Content Security Policy that lets only the page connect, to its own origin, and frames nothing but its own srcdoc.
  3. The page moves the token from the fragment into sessionStorage, fetches ui (relayed like /events, only for a root with workspace) and streams events with it, reconnecting with Last-Event-ID.
  4. It runs the document in an <iframe sandbox="allow-scripts"> whose srcdoc is a doctype, a policy with no network access, the bridge, and the document as published. The frame has an opaque origin, so it can't read the page or its token, and it reaches no server, except over WebRTC: an RTCPeerConnection in the frame sends to any host it names, in Chromium and WebKit alike, the known gap the agent-ui spec records. The page passes it nothing from the stream.
  5. The bridge is the frame's only way out. It defines jen.version and one request, jen.ask(context), which hands the page the context, any JSON value, and nothing else. The page accepts an ask only from the current frame and version, only while the user's click or key press is still active, and only under the 1 MiB bound. Safari drops a click's activation when the press takes focus out of a text input, so while one has focus, in the document or an open shadow root, the bridge cancels a press's mousedown default, keeping focus in the field, unless the press lands on another field, a slider, a select, editable text or a draggable element. The page posts an ask to messages as Asked from your UI, version <n>:, a newline and the JSON, which reaches the agent as an ordinary message from the owner. publish_ui's description tells the agent what the page does; no agent's instructions mention a UI, and nothing tells it how to answer.
  6. When the stream carries a publish_ui result, the page fetches ui, at most one fetch at a time and retrying one that fails, and swaps in the new version live. A published version is the only thing the agent changes on the page: its text replies never show there, and a bar shows only the page's own failures and the agent's error events.

Where agents run on a Mac

  1. On an Apple silicon Mac, the engine is jen's machine: a small Linux VM, Alpine with Docker's own engine, whose only job is to give jen an engine. The runtime and agents run in it as they run on any engine, so the diagram above holds inside it. jen never uses Docker Desktop there. Intel Macs are refused.
  2. It comes with npm install -g jen-ai, in the platform package @jen-ai/darwin-arm64, which npm installs only on an Apple silicon Mac: the machine's kernel, initramfs and read-only system disk (src/machine/, the Dockerfile's machine target), its launcher, and Docker's docker command. A checkout runs what npm run build:machine writes into dist/machine/. The machine's engine pulls jen's images as an installed jen does on Linux.
  3. The launcher, jen-machine (Swift, src/machine/launcher/), runs the VM inside its own process through Virtualization.framework, so the machine runs exactly as long as it does. The first command that needs the engine starts it, under a lock so two commands start one, and waits up to 60 seconds. jen stop all stops it after the runtime, and the launcher asks Linux to shut down, stopping the VM outright after 30 seconds.
  4. Only two things cross to the Mac, both over the VM's socket channel (vsock): the engine's socket, as engine.sock, which only the user can open, and every port a container publishes on 127.0.0.1, which the launcher mirrors on the Mac's 127.0.0.1 while the container runs, so the runtime's URL works as on Linux. A port something on the Mac already answers on is left to it and tried again later, so jen publishes the runtime on a port it finds free on the Mac. No folder of the Mac's is mounted, and nothing in the machine listens on its network.
  5. Each runtime name has its own machine, in ~/.jen/machines/<name>/: a data disk holding /var/lib/docker, so images, volumes and containers outlive stops and upgrades, beside the launcher's socket, its process ID, the system it booted and the console's log. When a new jen holds another system, the next command stops every agent through the runtime and restarts the machine on it. jen uninstall stops the machine and deletes the folder.

A query from jen, end to end

  1. jen, the jen-ai package installed from npm or a checkout linked with npm link, first refuses Node older than 26, then reaches the engine. On Linux that's through the user's docker command: it starts Docker Desktop when the engine doesn't answer, and refuses an engine older than 28.0. On a Mac it's jen's machine, through the docker command jen's package holds, started when it doesn't answer.
  2. jen @<name> <query> checks the three images, then finds the runtime. A checkout uses the images it builds, jen-runtime, jen-agent and jen-workspace. An installed jen uses its own release's, ghcr.io/reveer-ai/jen-<target>:<version>, which each release publishes, and pulls any that's missing. A running one gives the owner token from its container's environment and its port from docker port, with no container started. Otherwise jen reads the settings volume with a short-lived container of the runtime's image, asks for the settings in the terminal if there are none, and runs <name>-runtime with the socket, the settings passed by name and the port it had before, on 127.0.0.1. The runtime keeps running after the query. If any of jen's containers is on an image its name no longer refers to, jen first stops every root through the runtime, and each starts on the new image at its next message. Upgrading the package changes the version in the names, so this carries every agent onto the upgrade, and jen then removes the registry's images of other versions.
  3. It finds the root by its name in GET /agents, starts it if it's stopped, and opens the root's /events through the runtime's relay.
  4. The stream sends the saved items, then synced with the last item's position. Everything before that first synced is history, and isn't shown. Only then does jen post the query to /messages.
  5. Each later step's items arrive followed by one synced, never split by one. jen prints a line to stderr for each tool call, each message from a sub-agent and each error event, once the query's own message has arrived.
  6. The reply is the text of the first model response after the query's message with no tool call, read once a synced or another item says the response has ended. It goes to stdout, and jen exits.
  7. If the stream ends first, jen waits for the runtime, which may be being replaced, and resumes with Last-Event-ID while the root runs, or reports that it stopped. A root that gives up on its model ends the query with its notice, an error event marked gaveUp. Ctrl-C leaves the root working.

A message, end to end

  1. The owner sends POST /agents/<id>/messages to the runtime with the owner token. An agent messaging a sub-agent does the same through message_sub_agent, with its own token.
  2. The runtime checks the target is the caller's descendant (or parent), starting it first if it's stopped, and relays with the agent's token and Jen-From set to the caller.
  3. The agent's server inserts the message into the inbox and answers 202. Acknowledged means saved. It wakes the loop, or aborts the step in flight if the message is urgent.
  4. The loop settles any outstanding tool calls, delivers the inbox into the conversation in one transaction, and calls the model with its instructions.
  5. The response is saved at once, and every saved item streams out on GET /events through the runtime's relay.
  6. Its tool calls are settled next step: message_sub_agent, spawn_agent and the rest call the runtime, run_command posts to /workspace/commands, which runs the command in the agent's workspace, and read_file, write_file and edit_file get and put the file's raw bytes at /workspace/files?path=, beside it. A wait runs last, and the loop answers it from the inbox once a message arrives or no sub-agent owes a reply; until then the loop stops with the call open.
  7. A response with no tool calls ends the turn, and its text is the reply. A sub-agent's goes into its outbox in the same transaction and is posted to its parent through the runtime. A root's is the assistant message on its stream, where the owner reads it.
  8. With no calls left and an empty inbox, the loop ends. A sub-agent's reply wakes it again.

When things go wrong

  • Restart: all state is in the store, so the loop resumes. A call that may have been running is reported as unknown; later calls in its batch are marked not run. The model decides what to retry.
  • Woken by a message: the runtime starts the agent with JEN_WAKE, which holds the loop until its first message is saved, so recovery never calls the model without it.
  • Model failing: retried after 1, 5 and 25 s, each failure an error event. Then, unless a message has arrived meanwhile, which it retries for instead, the agent puts a notice in its outbox for its parent (a root shows it on its stream, marked gaveUp, until it's messaged again) and waits; any message retries.
  • Runtime notices: the runtime sends as runtime only what it alone saw: a child whose restarts ran out, or sub-agents still stopped when an agent starts.
  • Stop and delete: both act on the whole subtree. Stop removes the agent's container and then its workspace's, ending every process in it, and keeps both volumes; delete removes them too.
  • Workspace: a crash of the agent's process leaves its workspace running. A workspace whose first process dies comes back with its files. When an agent's restarts run out, its workspace container is removed. A file write goes to a temporary file and is renamed over its target only once every byte has arrived, so one cut short leaves the file as it was.
