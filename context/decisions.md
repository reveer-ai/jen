# Decisions

Newest first. Each entry gives the decision and why. When an entry is superseded, mark it and link the entry that replaces it.

## 2026-11-01

Made in [JEN-2](https://linear.app/reveer/issue/JEN-2), designing and scoping agent delegation. Only what was needed to scope the milestone was decided. The rest is for [JEN-10](https://linear.app/reveer/issue/JEN-10) and [JEN-11](https://linear.app/reveer/issue/JEN-11).

- **Logic lives in the weights.** Set by the maintainer as a core tenet. See [product.md](product.md). *Why:* the less behavior is coded, the less the architecture constrains what an agent can naturally do, such as a sub-agent asking its parent questions or spawning sub-agents of its own.
- **One runtime starts and stops every agent, the root included.** An agent and a sub-agent are the same image and code. They differ only in who started them (the user or a parent agent) and what they were granted, and the runtime holds both. *Why:* agents never share a host, so an agent can't start containers itself, and nothing in jen started any agent before this (the user ran `docker run`). Treating the root as the user's child means one mechanism instead of two.
- **The runtime owns the agent tree and guarantees no detached sub-agents.** A sub-agent's life is tied to its parent's place in the tree, not to the parent's process or turn, so a parent can sleep while its sub-agents run. Stopping an agent stops everything under it. *Why:* this is a reliability guarantee, which the tenet leaves to code.
- **The runtime applies capability grants. A grant can only narrow, and there is a bound on recursion.** An owner can give an agent at most what the owner has. Which bound (depth, count or spend) is for JEN-10. *Why:* delegation is the first time one agent hands power to another, and escalation or a runaway tree are security and reliability problems. The capability list stays small (model access and spawning) and grows as features arrive.
- **Messages between parent and child go both ways, and a message to a busy or sleeping agent is part of delegation.** It replaces JEN-9's `409` placeholder, in JEN-11. *Why:* a sub-agent that can ask its parent questions will reach it mid-turn or asleep. It's not a separate issue because it only arises from two-way messaging.
- **Delegation covers parent and child only.** Communication between other agents, such as two roots or two siblings, is a later milestone (see [plan.md](plan.md)). *Why:* JEN-1's single protocol already allows it, and permission to reach an agent you didn't start would be one more grant, so nothing here has to anticipate it.
- **An opening issue starts from a clean slate and decides only enough to scope.** Set by the maintainer at the start of JEN-2. See [conventions.md](conventions.md). *Why:* a milestone was written before the earlier ones were built, and what they delivered can change its shape. Design beyond the split belongs to the person doing each task.

## 2026-10-28

Made in [JEN-9](https://linear.app/reveer/issue/JEN-9), designing and building agent invocation. The full design is in `openspec/specs/` (capabilities `agent-protocol`, `agent-container` and `agent-store`), and the design document in `openspec/changes/archive/2026-10-28-serve-agent-over-http/`:

- **Agents speak jen's own protocol, over HTTP with Server-Sent Events.** `POST /messages` runs a turn and answers with its reply, and `GET /events` streams the conversation. Every client uses it, with no privileged path: a person with curl, a self-hoster, and later a parent agent, the UI and the npm package. *Why:* sending and watching are separate, so a client can send while its stream is open, and HTTP and SSE pass through the proxies, TLS and load balancers self-hosters already run. *Rejected:* WebSocket, since nothing needs the client to push on the stream, and it would mean writing our own framing and reconnection. A2A, which is built for interop between opaque agents from different vendors, and whose task model would shape jen's protocol around someone else's concepts. If interop matters later, A2A can be a facade at the edge.
- **The stream carries saved conversation items only, and resumes by position.** Each event's ID is the item's position in the store, and `Last-Event-ID` resumes after it. A turn's items are sent once it's saved, so a failed turn sends nothing. *Why:* every event is durable and never retracted, so reconnecting is exact and several clients can watch at once. Progress within a turn and token deltas become separate event types when the UI engine ([JEN-3](https://linear.app/reveer/issue/JEN-3)) needs them.
- **Every request needs the bearer token in `JEN_TOKEN`, and the agent won't start without it.** This is explicitly a minimum, not an auth design. *Why:* an exposed agent spends its owner's model credits, and later runs its tools. Auth gets designed in depth later, with hosting and with agents calling agents (see [plan.md](plan.md)).
- *To be replaced in [JEN-11](https://linear.app/reveer/issue/JEN-11), decided 2026-11-01:* **An agent runs one turn at a time, and a message during a turn gets `409`.** It's a placeholder. *Why:* what a busy agent does with a message belongs to [JEN-2](https://linear.app/reveer/issue/JEN-2), along with how delegation works.
- **No `jen` CLI until distribution.** Starting an agent is `docker run`. *Why:* a wrapper belongs with packaging in [JEN-4](https://linear.app/reveer/issue/JEN-4), and starting an agent from another agent belongs to JEN-2.

## 2026-10-27

- **Finished implementation is committed and opened as a pull request without asking.** Set by the maintainer after JEN-8's implementation. It covers only a clean finish: every task done and verified. *Why:* review happens on the pull request, so asking first only adds a round-trip. See [conventions.md](conventions.md).

Made in [JEN-8](https://linear.app/reveer/issue/JEN-8), running the agent in a container. The full design is in `openspec/specs/` (capabilities `agent-store` and `agent-container`):

- **The container is the only supported way to run an agent.** The store and `respond` are unit-tested in-process, because CI has no container runtime, but the host isn't a place to run agents. *Why:* as an agent gains tools and preinstalled software, its image is what makes it that agent. Code run anywhere else isn't the same agent.
- **The conversation is stored as one JSON row per item**, in a single `items` table in `/state/agent.db`, with each turn appended in one transaction. *Why:* items stay exactly in the port's shape for whatever reads them later. Turn boundaries can be derived, since each turn starts with a user message, and nothing queries inside items yet. A column per field would change every time the item union does.
- *Superseded 2026-10-28 by jen's own protocol over HTTP:* **The one-shot entrypoint (one message per run, from the arguments) stands until [JEN-9](https://linear.app/reveer/issue/JEN-9).** JEN-9 replaces its interface rather than extending it. *Why:* it's the smallest thing that proves an agent exists and remembers. The store and `respond` carry over unchanged.

- **The maintainer opens each proposal discussion, and the agent drafts only after they've aligned.** Set by the maintainer at the start of [JEN-8](https://linear.app/reveer/issue/JEN-8). *Why:* it shows early whether agent and maintainer see the problem the same way. The maintainer's view isn't the default answer, and the agent is expected to push back where it disagrees. See [conventions.md](conventions.md).

## 2026-10-26

Made in [JEN-7](https://linear.app/reveer/issue/JEN-7), building the agent loop and model port. The full design is in `openspec/specs/` (capabilities `agent-loop`, `model-port` and `openai-responses-adapter`):

- **jen keeps the conversation, and never relies on the provider keeping it.** Every model call sends the whole conversation. The Responses adapter sets `store: false`, which turns off OpenAI's stored response state, and never refers to a stored response or item. That isn't a retention guarantee: what a provider keeps otherwise, such as OpenAI's abuse-monitoring logs, depends on its policies and the account's data controls. *Why:* jen can then change model or provider partway through a conversation, and any agent can read it. Provider-side state exists only on OpenAI, and jen would still need its own copy for every other API.
- **The model port is request/response, with no streaming yet.** *Why:* nothing reads a partial turn until the UI engine ([JEN-3](https://linear.app/reveer/issue/JEN-3)). Streaming is added then.
- **The port and the loop carry only what something uses.** System instructions, token usage, cancellation, typed model errors, reasoning across turns and a step limit are each added when a caller needs them. *Why:* every field added speculatively is one each future adapter has to map, and guessing ahead is how a port ends up copying one vendor's shape.
- **TypeScript runs directly on Node 26, with no build output.** `tsc --noEmit` is the build, and `erasableSyntaxOnly` keeps the code to what Node can strip. *Why:* nothing consumes emitted JavaScript yet. Node won't strip types inside `node_modules`, so publishing to npm will need an emit step, which [JEN-4](https://linear.app/reveer/issue/JEN-4) adds.
- **The Responses adapter authenticates with an API key only, for now.** It doesn't yet support OpenAI's [Sign in with ChatGPT plan usage](https://developers.openai.com/siwc/token-sharing-open-source), which bills a user's ChatGPT plan through an OAuth token. *Why:* it's in preview, and an API key covers everything JEN-7 needed. It can be added later as a second auth option on the adapter, with no change to the port.

- **Virtually all feature work goes through OpenSpec, and the proposal is aligned on before anything else.** Set by the maintainer at the start of [JEN-7](https://linear.app/reveer/issue/JEN-7). *Why:* the proposal is where agent and maintainer agree on what's being built before design and code commit to it. See [conventions.md](conventions.md).

Made in [JEN-1](https://linear.app/reveer/issue/JEN-1), designing the jen agent:

- **A point is about 4 hours of the maintainer's time, and capacity is about 8–9 points a week.** *Why:* agents write nearly all the code, so the scarce resource is the maintainer's time, not the coding. Estimating that resource is what makes cycle planning honest. See [conventions.md](conventions.md).
- **A jen agent is written in TypeScript on Node.** *Why:* the agents are the UI, and generated UI will almost certainly be web tech, so one language runs from the agent to the renderer. The strongest model-client options and npm distribution are TypeScript-native too.
- **jen builds its own agent loop. No third-party agent SDK.** *Why:* the harness is jen's product. Delegation and self-presentation have to be native to the loop, not fitted around another SDK's shape. A *model* SDK underneath is fine.
- **Model access goes through a port that jen defines, with adapters behind it** (ports and adapters, also called hexagonal architecture). The port states what jen needs in jen's own terms. Only an adapter imports a model SDK, and no SDK type crosses the port. The first adapter wraps the official **OpenAI SDK** and targets the **Responses API**. It reaches OpenAI directly, and open models and Claude through OpenRouter's Responses endpoint, which translates for every model it hosts (beta as of this date). A second adapter on the same SDK targets **Chat Completions**, for endpoints that speak only that (Gemini, Mistral, DeepSeek, local servers and others). A native **Anthropic SDK** adapter comes after that. The second implementation from day one is a scripted fake model, which is also the loop's test fixture. No provider registry, config-driven adapter selection or plugin system until a real case needs one. *Why:* jen must never be tangled with a model SDK, so SDKs can be swapped or added. The official SDKs are closest to the source, because each vendor maintains its own and tracks its API. The main risk is a port that quietly copies the OpenAI SDK's shape. The fake catches the obvious cases, two adapters for two APIs of one SDK catch more, and the Anthropic adapter is the real test. Responses goes first because it's OpenAI's current API, carries reasoning across turns for OpenAI's reasoning models, and is where compatible endpoints are heading.
  - *Rejected:* pi-ai (`@earendil-works/pi-ai`). It's a good, lightweight multi-provider client, but it normalizes over the official SDKs. Behind jen's port it would be a wrapper inside a wrapper, and it pins SDK versions behind current: Anthropic 0.129 against 1.3.0 as of this date. Also rejected: the Vercel AI SDK, whose Agent and UI-streaming layers lean into ground jen means to own, and TanStack AI, which is a framework rather than a client and reached 1.0 on 2026-10-22.
- **Each jen agent is an OCI container** with its own filesystem, a mounted volume for state that outlives the container, and **SQLite** on that volume as its database. Isolation strength (plain Docker, gVisor, microVMs) is a deployment setting, because the same image runs under all of them. *Why:* cloud, cloud-less and local targets all run Linux containers. SQLite runs in-process and an agent's database has one owner, so it's the fastest fit. Revisit it only if a concrete workload outgrows it.
- **One protocol covers user→agent, agent→agent and parent→child.** Agents talk over the network, never through a shared host. A parent's authority over a child (spawn, stop, inspect) is a permission and a runtime operation, not a second protocol. *Why:* a sub-agent is a jen agent, so peers and children differ in authority, not in wire format. Talking over the network keeps local and remote agents identical, so delegation ([JEN-2](https://linear.app/reveer/issue/JEN-2)) and hosting ([JEN-4](https://linear.app/reveer/issue/JEN-4)) don't force a redesign.

## 2026-10-24

- **The agent is the project's manager. The maintainer is its lead and customer.** The lead sets direction and makes the calls that shape jen. The agent owns everything else: Linear, the record, conventions, skills and prompts. *Why:* the maintainer works on the project only through agents. One general role statement covers duties nobody has listed yet, so the prompt doesn't have to enumerate them.
- **`context/` is the project's source of truth.** Agents keep it. `AGENTS.md` points to it, and `CLAUDE.md` imports `AGENTS.md`. *Why:* all work goes through agents. Any agent (Claude Code, Codex or another) or engineer who checks out the repo should get the full picture without depending on one tool's private memory.
- **OpenSpec is initialized in the repo** (1.15.0, `spec-driven` schema) for Claude Code and Codex, under [JEN-5](https://linear.app/reveer/issue/JEN-5). How it's used gets settled the first time a task needs it.
- **Fresh start.** A new Linear workspace (`reveer`), team `jen` and repo `reveer-ai/jen`, with no "v2" naming.
- **The first project is "Agent harness & UI engine"**, with four milestones in this order: Agent container, Agent delegation, UI engine, Distribution and hosting. *Why:* a project is a bounded effort, and the team already stands for the product. Delegation is its own milestone because a sub-agent is the same kind of agent; what's new is the relationship between agents. The UI engine comes before hosting because it's how a user uses jen at all. Local use falls out of building it, and hosting is mostly a question of transport.
- **Target date 2026-11-29, with one milestone per one-week cycle.** *Why:* that's about a week per milestone, plus a slack week. It errs on the safe side and can be pulled in.
- **Milestones get no separate target dates.** *Why:* a milestone's size isn't known until its design issue is done.
- **Each milestone is scoped by its own opening issue**, not in an up-front scoping session. *Why:* scoping before getting into the problem has gone wrong before.
